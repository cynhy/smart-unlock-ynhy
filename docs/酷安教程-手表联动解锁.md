# 手表联动的亮屏自动解锁：免 root，手机独立运行

适用环境：小米 15，HyperOS 3（V816），Android 16，未 root；另在 LineageOS 设备上做过交叉验证。
效果：手表处于连接状态时，点亮屏幕后自动完成 PIN 输入并进入桌面。HyperOS 约 1 秒，AOSP 类系统约 2 秒。手表未连接时保持原有锁屏流程。

---

## 一、概述

### 1.1 能做到什么

在手表连接的前提下，把原本需要手动输入的锁屏 PIN 交给手机自动完成。整套逻辑运行在手机本地，不依赖电脑，不需要 root，也不需要改动系统分区。

支持同时登记多个设备（例如手表 + 耳机），任意一个在线即可触发。

### 1.2 做不到什么

无法在后台静默提交密码。Android 的安全模型不允许应用或 shell 直接验证锁屏凭证，密码键盘必须实际出现并被注入按键，输入才会生效。因此解锁过程中键盘会短暂显示，这是机制决定的，不是实现上的偷懒。

速度有下限。当前实现从亮屏到进入桌面约 1 至 2 秒，主要开销来自系统唤醒、键盘挂载和按键注入，继续压缩需要改动系统组件。

### 1.3 一个必须知道的局限：只判断连接，不判断佩戴

脚本判断的是「目标蓝牙设备是否与手机保持连接」，不是「手表是否戴在手上」。

两者的差别很实际：手表摘下来放在桌上，只要没断开蓝牙，手机依然会自动解锁。也就是说，这套方案防的是"忘带手表"，不是"手表被放在旁边"。

原因在于佩戴状态由手表自身的光学或电容传感器判定，属于厂商私有数据，Android 没有标准接口把它暴露给第三方。系统级方案里只有华为的「增强模式」做到了这一点，条件是手表端配合上报，且仅限指定机型。

可行的缓解手段有限，都属于降低暴露面而非根治：

1. 摘下手表时顺手在系统里断开连接，或直接关闭手表蓝牙。
2. 加 RSSI 门槛，避免手表落在较远处仍触发（对手表放在同一张桌上的情况无效）。
3. 配合可信地点使用，把自动解锁限制在家里或公司。

如果对安全性要求较高，建议不开这套方案，改用系统级的信任设备或干脆保持手动解锁。

### 1.4 与传统「智能解锁」的区别

系统自带的蓝牙解锁属于信任设备机制：设备连接时系统直接判定为可信，锁屏不出现。本文方案走的是注入路径，等价于"有人替你按了密码"。前者更快也更安全，但多数厂商只开放给自家穿戴设备，具体见第八节。

## 二、原理

### 2.1 为什么 shell 能向安全锁屏注入按键

Android 的锁屏属于安全窗口，普通应用和辅助功能都无法向其中注入事件。但 adb shell 与 Shizuku 的运行身份都是 `uid 2000(shell)`，持有 `INJECT_EVENTS` 权限，可以向安全窗口注入按键。这是整套方案的基础。

### 2.2 两分钟可行性自测

不同机型对注入的拦截程度不同，建议先确认再继续：

1. 锁屏并上滑，调出 PIN 键盘。
2. 执行 `adb shell input keyevent 8`（对应数字 1）。
3. 观察右下角按钮，正常表现是从「返回」变为「删除」。

出现这个变化，说明按键确实进入了密码框；没有变化则说明该机型拦截了注入，本方案不适用。

### 2.3 解锁流程时序

```
屏幕点亮
  └─ logcat 事件 power_screen_state [1,...]
       ├─ 6 秒防抖检查
       ├─ 等待 mWakefulness=Awake
       ├─ 检查 Display State=ON（排除防误触）
       ├─ 检查锁屏状态
       ├─ 检查目标设备在线
       └─ 唤出键盘 → 注入 PIN → 校验结果
```

只有五项检查全部通过才会执行注入，任何一项不满足都直接跳过，不产生副作用。

## 三、部署

### 3.1 环境要求

1. 手机安装并运行 Shizuku。非 root 设备需要用「无线调试」激活一次，这是唯一无法绕过的前提。
2. 目标设备（手表或耳机）已在系统蓝牙设置中完成配对。
3. 仅使用电脑部署时，需要 adb 与 USB 调试授权。

### 3.2 方式 A：手机端部署包（不需要电脑）

压缩包 `手表自动解锁-手机端部署包.zip` 内三个文件：

| 文件 | 作用 |
| --- | --- |
| `一键部署.sh` | 交互入口，询问密码和设备名后调用 deploy.sh |
| `deploy.sh` | 实际部署逻辑 |
| `说明.md` | 使用说明与常见问题 |

步骤：

1. 解压到手机任意目录，两个 .sh 必须放在同一个文件夹。
2. 用 MT 管理器长按 `一键部署.sh` → 执行 → 身份选择 Shizuku。
3. 按提示输入锁屏密码和设备名称关键词。

也可以直接在 Shizuku 终端里执行：

```sh
sh /sdcard/watch-unlock-pkg/一键部署.sh
```

带参数一步到位：

```sh
sh /sdcard/watch-unlock-pkg/一键部署.sh <锁屏PIN> "OPPO Watch,MOONDROP"
```

### 3.3 方式 B：电脑 adb

```sh
adb push deploy.sh /data/local/tmp/
adb shell sh /data/local/tmp/deploy.sh -p <锁屏PIN> -w "OPPO Watch,MOONDROP"
```

注意 `-s <序列号>` 用于指定目标，同时连多台设备时必须加。

### 3.4 参数说明

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `-p` | 是 | 锁屏数字密码，脚本内部换算成键码，不需要手工对照 |
| `-w` | 二选一 | 设备蓝牙名称中的关键词，不区分大小写，支持逗号分隔多个 |
| `-m` | 二选一 | MAC 末四位，例如 `EE:FF`。名称重复或匹配失败时使用 |

脚本按名称在系统已配对列表中查找设备，不需要填写完整蓝牙地址。

`deploy.sh` 是自包含的：写入配置、生成守护脚本与停止脚本、清理旧实例、启动新实例，最后输出自检结果。两种方式用的是同一个脚本，行为完全一致。

### 3.5 输出解读

```
>>> writing config
    pin_len=6  watch=OPPO Watch,MOONDROP  mac=none
>>> writing daemon script
>>> writing stop script
>>> stopping old instance
>>> starting daemon
>>> deployed
watch_name  : OPPO Watch,MOONDROP
match_mac   : XX:XX:XX:XX:75:D8
watch_online: yes
locked      : yes
awake       : no
pin_keys    : 9 12 15 10 13 16
>>> log: /sdcard/watch-unlock/wu.log
```

上面这次实际输出里 `match_mac` 是耳机而不是手表：当时手表不在身边，耳机在线，脚本按顺序跳过了离线的那台。

| 字段 | 含义 |
| --- | --- |
| `match_mac` | 当前在线的那台设备，为空说明关键词与系统蓝牙列表不符 |
| `watch_online` | 是否有设备处于连接状态 |
| `locked` | 当前是否处于锁屏 |
| `awake` | 屏幕是否已唤醒 |
| `pin_keys` | 由 `-p` 换算出的键码 |

`watch_online` 为否时不会执行解锁，属正常状态。

### 3.6 多设备与多目标

同一台手机可以登记多个触发设备。`-w "OPPO Watch,MOONDROP"` 表示两者任一连接即可触发。

匹配时按关键词顺序逐个检查，只有找到"已连接"的设备才返回成功。这一点在出门只带耳机、手表留在家里时很关键：如果只判断第一个匹配到的名称，会出现"设备明明连着却报告离线"的误判。

### 3.7 常用命令

手机端（Shizuku 终端或 MT 管理器）：

```sh
sh /sdcard/watch-unlock/wu-daemon.sh --check          # 查看状态
sh /sdcard/watch-unlock/deploy.sh --stop              # 停止
tail -n 30 /sdcard/watch-unlock/wu.log                # 查看日志
```

电脑端：

```sh
adb shell sh /sdcard/watch-unlock/wu-daemon.sh --check
adb shell sh /sdcard/watch-unlock/deploy.sh --stop
adb shell "tail -n 30 /sdcard/watch-unlock/wu.log"
```

部署完成后可以断开 USB。守护进程以 shell 身份运行，实测 `adb kill-server` 断开重连后仍然存活。

## 四、实现细节

### 4.1 事件触发

守护进程监听 `logcat -b events` 中的 `power_screen_state` 事件，只在字段为 `[1,` 时处理。全程阻塞读，不轮询，不持有 wakelock，待机开销可以忽略。

不使用定时轮询的原因很简单：轮询一秒一次会让 CPU 长期处于唤醒状态，而屏幕点亮本身就会产生事件，没有理由重复检测。

### 4.2 唤出键盘：dismiss-keyguard 与上滑的取舍

最初的实现模拟手工操作：上滑、等待动画、输入密码。这种方式在普通锁屏上可用，但在音乐类应用接管锁屏时会失败——上滑事件被该界面接收，密码键盘没有出现，后续按键全部失效。

改为执行 `wm dismiss-keyguard` 后问题消失。该命令直接请求系统展示密码输入界面，不经过手势识别。

实测对比（各三次）：

| 场景 | 上滑 120ms | 上滑 300ms | wm dismiss-keyguard |
| --- | --- | --- | --- |
| 普通锁屏 | 3/3 | 3/3 | 3/3 |
| 音乐锁屏 | 失败 | 偶发成功 | 成功 |

需要说明的是，`wm dismiss-keyguard` 只负责唤出界面，不涉及凭证验证。真正解锁仍然依靠 PIN 注入，这一点无法绕过。

### 4.3 跨 ROM 自适应

`wm dismiss-keyguard` 在 AOSP 类系统上行为不同：设备设有密码时通常不会唤出键盘。

脚本启动时检测一次系统类型：`dumpsys window policy` 中存在 `mIsShowing=` 字段（MIUI / HyperOS 特征）时，主路径用 `dismiss-keyguard`；否则用长上滑。另一条路径保留为失败兜底。

实测结果：HyperOS 走 `dismiss-keyguard`，约 1 秒；LineageOS（Redmi Note 11T Pro，Android 17 userdebug）走上滑，约 2 秒。

### 4.4 设备在线判定

不同 ROM 的 `dumpsys bluetooth_manager` 格式差异较大，脚本按两条路径判断：

1. MIUI / HyperOS：配对列表中不含连接状态，改查 `==== StateMachine for <MAC> ====` 段落里的 `mCurrentState: Connected`。
2. AOSP / LineageOS：配对行里直接带 `[ACL BR/EDR:Y]` 标记，含该标记即视为连接。

名称到 MAC 的转换通过解析配对列表完成：取最后一个 `]` 之后的内容作为设备名，与关键词做不区分大小写的匹配，命中后取行首的 MAC。

### 4.5 保护机制

为了避免误操作导致设备被锁定，设置了六条限制：

1. 同一事件 6 秒内不重复处理。
2. 连续失败 3 次进入 10 分钟冷却。
3. 屏幕未唤醒（`mWakefulness` 非 `Awake`）时不注入。
4. 显示已熄灭（`Display State=OFF`）时不注入。
5. 注入后轮询等待解锁完成，并在重试前确认密码键盘仍存在；键盘已消失时放弃重试，避免 DEL 和密码被打进刚解锁的桌面。
6. SIM 卡处于 PIN / PUK / 网络锁状态时直接跳过；注入前还会确认当前焦点确实是锁屏，而不是 SIM 卡或其它凭证界面。

第五条是本次新增的。校验密码通过后，keyguard 还有一段退场动画，`mIsShowing` 会在这段时间里继续返回 `true`，原来的固定 `sleep 0.7` 会把它误判成失败。现在改为最多轮询 3 秒；若仍未解锁，先用 `uiautomator dump` 确认 `keyguard_pin_view` 还在，才允许清空并重输。键盘不在就直接放弃，不消耗失败次数。

第六条针对重启场景。启用 SIM 卡 PIN 后，开机时屏上的键盘属于 SIM 卡，不是手机锁屏，注入手机 PIN 会连续输错，三次就可能锁卡并需要 PUK。脚本先读 `gsm.sim.state`，出现 `PIN_REQUIRED`、`PUK_REQUIRED` 等值就跳过并写日志；再做一次焦点校验，焦点不在 `NotificationShade` / `StatusBar` 等锁屏窗口时同样跳过。两层都不过才允许按键。

第四条是实践中补上的。手机屏幕朝下放在桌上，或有东西压住传感器上半部分时，系统会进入防误触模式：`mWakefulness` 仍是 `Awake`，但显示已经熄灭，锁屏处于黑屏且不接收输入。此时注入全部无效，还会把失败计数用光。现在的做法是先查显示状态，熄灭就直接跳过。

### 4.6 冷却实现

早期版本用 `sleep 600` 实现冷却，副作用是守护进程整整十分钟不处理任何事件。现在改为记录截止时间戳，冷却期间照常接收事件，只跳过注入动作，结束后自动恢复。

## 五、配置文件

位置：`/sdcard/watch-unlock/config.conf`

```
PIN_TEXT="<锁屏PIN>"
PIN_KEYS="9 12 15 10 13 16"
WATCH_NAME="OPPO Watch,MOONDROP"
WATCH_MAC_SUFFIX=""
DEBOUNCE=6
MAX_FAILS=3
COOLDOWN=600
```

| 键 | 说明 |
| --- | --- |
| `PIN_TEXT` | 密码原文，注入时用 `input text` 一次性提交，由 `-p` 自动生成 |
| `PIN_KEYS` | 密码对应的键码，保留用于自检输出，一般不需手改 |
| `WATCH_NAME` | 设备名称关键词，逗号分隔 |
| `WATCH_MAC_SUFFIX` | 可选，MAC 末四位 |
| `DEBOUNCE` | 防抖窗口，秒 |
| `MAX_FAILS` | 连续失败几次进入冷却 |
| `COOLDOWN` | 冷却时长，秒 |

`MAX_FAILS` 与 `COOLDOWN` 建议保持默认值。它们是设备被意外锁定的唯一保护，调激进了一旦密码不同步就会锁死。

修改配置后需要重启守护进程生效：

```sh
adb shell sh /sdcard/watch-unlock/deploy.sh --stop
adb shell "nohup sh /sdcard/watch-unlock/wu-daemon.sh >/dev/null 2>&1 &"
```

或者重新执行一次部署命令，会覆盖配置并重启。

## 六、保活

Shizuku 在非 root 环境下重启后不会自动恢复，需要借助 MacroDroid 保活。新建两条宏，执行方式都选 Shizuku。

**开机启动**
触发器：「设备启动，延迟 90 秒」和「应用启动 → Shizuku」
约束：「Shizuku 运行中」
动作：Shell

```sh
nohup sh /sdcard/watch-unlock/wu-daemon.sh >/dev/null 2>&1 &
```

**定时兜底**
触发器：「每 15 分钟」
动作：同上

守护进程带单实例锁，重复执行不会产生多个进程。

由于密码存放在配置文件中，宏命令本身不含任何敏感信息，被查看也不会泄露 PIN。

## 七、常见问题

**按键无反应，锁屏仍在**

查看日志中是否出现 `retry: clear and inject again`。若未出现，说明密码界面已弹出但按键未生效，可把 `sleep 0.3` 调整为 `0.5`。若出现 `abort: no keypad, refuse to inject`，说明键盘已经消失、脚本主动放弃了重试，通常代表上一次其实已经解锁成功。若持续失败，回到第二节重新做注入自测。

**watch_online 为否，但设备已连接**

检查 `match_mac` 是否为空。为空说明关键词与系统蓝牙列表中的显示名不符，可只填其中一段（例如 `OPPO` 或 `Watch X`），也可以用 `-m` 指定 MAC 末四位。

**多个设备名用了中文逗号**

用 `，` 分隔时脚本会自动转成半角，无需人工处理。但如果直接编辑 `config.conf`，请使用半角逗号 `,`。写成中文逗号时整串会被当成一个关键词，表现为始终匹配不到设备、完全不触发。

**设备曾被删除配对**

系统蓝牙列表里已不存在该设备时，名称匹配会失败。重新配对即可，守护进程无需改动，下次亮屏会自动识别。

**亮屏后毫无反应，日志只有 `skip: display off`**

手机处于防误触模式，多半是屏幕朝下或传感器上半部被遮挡。翻过来或按音量键退出即可，脚本不会因此浪费尝试次数。

**重启后失效**

Shizuku 停止导致。重新激活后由 MacroDroid 宏拉起，这是本方案唯一的日常维护点。

**重启后日志只有 `skip: sim locked` 或 `skip: not on keyguard`**

启用了 SIM 卡 PIN 时属于正常现象：开机时屏上是 SIM 卡键盘，脚本不会注入手机 PIN，避免把 SIM 卡输错锁死。手动输入 SIM PIN 后，下一次熄屏再亮屏就会恢复自动解锁。`skip: not on keyguard` 后面会跟当前焦点窗口，可据此判断当时停在哪个界面。

**换手机、换设备或换密码**

换手机重新执行一次部署命令；换设备修改 `-w` 关键词；换密码重新执行部署。

**能否与系统自带的蓝牙解锁共存**

可以。系统级解锁生效时锁屏不会出现，脚本检测到未锁屏会直接跳过，不会冲突。

**会不会因为误判把手机锁死**

脚本的三次失败冷却就是为了兜住这种情况。即使真发生，冷却结束后会重新尝试，不会无限累积。

## 八、各品牌蓝牙解锁的开放程度

系统级的「蓝牙设备解锁」并非所有厂商都开放给第三方设备。整理如下，供判断可行性时参考。

| 品牌 / 系统 | 是否允许非本品牌设备 | 说明 |
| --- | --- | --- |
| 小米、红米（MIUI / HyperOS） | 否 | 系统内置的「蓝牙设备解锁」仅识别小米、红米的手环与手表。社区多次提出开放需求，官方未支持。实测将配对信息改为其他品牌设备后仍会弹出锁屏 |
| 华为（HarmonyOS） | 部分 | 「智能解锁」普通模式可添加任意已配对蓝牙设备；「增强模式」仅支持指定机型，如 Watch GT 2 Pro 系列、WATCH 3 / 3 Pro、Watch GT 3 系列等，2021 年 10 月后发布的多数手表支持，WATCH 5 不支持增强模式 |
| 荣耀（MagicOS） | 部分 | 与华为同源，普通模式通用，「增强模式」限华为 / 荣耀系手表 |
| OPPO、一加（ColorOS） | 是 | 「智能解锁」的可信设备支持蓝牙与 WiFi，可同时添加多个，未限制品牌 |
| vivo、iQOO（OriginOS） | 是 | 「智能解锁」的信任设备可添加任意已配对蓝牙设备 |
| 三星（One UI） | 是 | Smart Lock 的可信设备为 Android 原生实现，支持任意蓝牙设备 |
| 原生 Android（Pixel 等） | 是 | 同上 |

几点补充。

厂商会随版本调整策略，上表以当前公开资料和实测为准，最终以设置界面中能否选中目标设备为判断依据。

判断方法：把设备正常配对后，进入「智能解锁 / 可信设备」列表，如果目标设备可以被选中并完成设置，就是开放的；如果列表里只出现自家设备，或目标设备被置灰，就是受限的。

受限的品牌同样可以使用本文的方案，区别只是走注入路径，而不是系统级的信任设备路径。

## 九、安全说明

这套方案的本质是在特定条件下替用户输入锁屏密码，客观上降低了设备的安全性，使用前需要明确接受这一点。

1. 佩戴状态无法判断，手表放在桌上只要蓝牙不断也会解锁。这条是本方案最大的安全短板，接受不了就不要用。
2. 摘下手表后必须确认锁屏恢复正常，这是部署后应当第一时间验证的内容。
2. 密码以明文和键码两种形式保存在 `config.conf` 中。Android 11 之后普通应用无法随意读取共享存储，但文件管理器可以查看，介意时可自行加密存放。
3. 账号类凭证（微信、支付宝）不受影响，锁屏 PIN 只解屏幕。
4. 脚本与本文件不要一并转交他人。

## 十二、部署后验证清单

按顺序做一遍，能覆盖绝大多数配置错误。下面的命令以电脑端写法为例，在手机 Shizuku 终端里把 `adb shell` 去掉即可，效果一致。

**第一步，看自检**

```sh
adb shell sh /sdcard/watch-unlock/wu-daemon.sh --check
```

`match_mac` 不应为空，`watch_online` 应为 `yes`。为空说明关键词与系统蓝牙列表的显示名不符。

**第二步，亮屏三次**

熄屏后点亮，连续三次。日志应出现三组：

```
inject: watch online + locked (mode=dismiss)
result: unlocked
```

三次都成功说明主路径稳定。出现 `retry: alternate path` 说明主路径失效但兜底接住了，可以正常用，但建议反馈具体的 ROM 版本。

**第三步，负向测试（可选）**

临时把关键词换成一个已配对但不在线的设备，确认不会误触发：

```sh
adb shell sh /data/local/tmp/deploy.sh -p <密码> -w "TWS"
adb shell sh /sdcard/watch-unlock/wu-daemon.sh --check   # watch_online 应为 no
```

测完记得换回正式配置。

**第四步，摘表测试（必做）**

摘下手表并断开连接，点亮屏幕，确认仍然需要输入密码。这一步验证的是锁屏没有被永久改变，是整套方案的安全底线。

**第五步，重启测试（可选）**

重启手机，确认 Shizuku 恢复后由 MacroDroid 宏拉起守护进程。若未拉起，检查宏的 Shizuku 执行权限。

## 附录 A：将其他品牌设备伪装为小米设备的尝试

系统既然提供「蓝牙设备解锁」，是否有办法让非小米设备也触发，做过一轮验证，记录如下。

MIUI 的相关逻辑位于 `com.android.keyguard.MiuiBleUnlockHelper`，密钥保存在 Secure settings 的四个键中：`bluetooth_address_to_unlock`、`bluetooth_name_to_unlock`、`bluetooth_key_to_unlock`、`bluetooth_unlock_status`。shell 有写入权限。

据此设想的路径是：写入目标设备的真实 MAC 与名称，在设备端实现对应的 BLE GATT 服务，完成挑战应答，同时保证连接信号强度满足 `verifyBLEDeviceRssi` 的判断。

实际结果：

1. 四个键写入成功。
2. 使用伪造地址测试，锁屏正常出现，说明不存在验证失败即放行的漏洞。
3. 使用设备的真实 MAC（通过设备自身 adb 读取 `settings get secure bluetooth_address`）并保留原密钥，锁屏仍然出现。
4. 结合 `miui-framework` 中的 `MATCHED_BLUETOOTH_KEY_TO_UNLOCK` 常量判断，校验依据是配对阶段生成的协商密钥，而非地址与名称。
5. 直接发送解锁广播被权限拒绝：

```
SecurityException: Permission Denial: not allowed to send broadcast
com.miui.keyguard.bluetoothdeviceunlock from uid=2000
```

6. 尝试抓取 HCI 日志分析握手过程，日志位于 `/data/misc/bluetooth/logs/btsnoop_hci.log`，非 root 无法读取；`adb bugreport` 返回 `Failed to connect to dumpstatez service: Connection refused`。

结论是在未 root 的设备上，该路径不具备可行性。要推进需要满足以下条件之一：取得 root 权限、使用硬件 BLE 嗅探设备、或在目标设备上完整实现该协议（前提是设备为 Android 系统、允许安装第三方应用、能长期运行 GATT 服务）。

本文的注入方案不依赖上述条件，是当前环境下可落地的做法。
