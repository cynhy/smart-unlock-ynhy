# 蓝牙设备解锁 1.0：亮屏自动输 PIN，最快 550ms 进桌面

> 适用环境：小米 15 / HyperOS 3 / Android 16（主测），Redmi 22041216C / LineageOS 24 / Android 17（交叉验证）。
> 效果：勾选的蓝牙设备在线时，屏幕一点亮就自动完成 PIN 输入。两台实测分别 550～730ms 与 960～1070ms。
> 不需要 root，不需要电脑。

---

## 一、概述

### 1.1 它能做什么

装一个 APK，打开、勾选设备、输一次 PIN。之后每次亮屏，只要勾选的设备在线，应用就会替你输入锁屏密码并进入桌面。

条件不再是「一块手表」，而是任意已配对的蓝牙设备：手表、手环、耳机、音箱、键盘、另一台手机都可以，可以同时勾选多个。

| 能力 | 说明 |
| --- | --- |
| 自动解锁 | 亮屏触发，实测 550～1070ms 进入桌面 |
| 任意蓝牙设备 | 只要已配对且会回连，不限品牌 |
| 逐设备启用 | 未勾选的不参与判定，新设备默认不勾 |
| 多设备模式 | 任一在线（默认）或全部在线（AND） |
| WiFi 条件 | 每个 SSID 独立开关，可设为必要条件 |
| 临时暂停 | 15 分钟 / 1 小时 / 4 小时，重启不丢 |
| 日志页 | 独立二级页面，2.5 秒自动刷新 |
| 一键清理 | 停进程、删配置，保留勾选 |
| 中英双语 | 跟随系统语言，也可在应用内手动切换 |
| 语言切换 | 标题右侧按钮，自动 / 中文 / English 三态循环 |

### 1.2 三个前提

1. 锁屏方式是 **PIN 码**（纯数字）。图案、混合密码不支持，原因见第十一节。
2. 装了 **Shizuku** 并正在运行。不需要 root。
3. 设备已在系统蓝牙设置里完成配对。

这三条无法绕过。Android 的锁屏属于安全窗口，只有 shell 身份（uid 2000）持有 `INJECT_EVENTS` 权限，普通应用和辅助功能都注入不进去。Shizuku 的作用就是把 shell 身份借给应用。

### 1.3 和系统自带的「蓝牙解锁」有什么区别

系统级方案是厂商实现的信任设备机制：设备连接时直接把手机标记为可信，锁屏不出现，速度也更快。

代价是不通用。小米的「蓝牙设备解锁」只认自家手环手表；华为的「智能解锁」普通模式虽然接受任意蓝牙设备，但更安全的「增强模式」只支持指定机型。

本方案反过来：对设备没有品牌要求，代价是每次解锁会有一瞬间的键盘动画，以及依赖 Shizuku。

### 1.4 一个必须知道的局限

应用判断的是「设备是否与手机保持连接」，不是「设备是否戴在身上」。

手表摘下来放在桌上，只要蓝牙没断，手机照样会自动解锁。佩戴状态由设备自身的光学或电容传感器判定，属于厂商私有数据，Android 没有标准接口开放给第三方。系统级方案里只有华为的增强模式做到了，且需要设备端配合上报。

可行的缓解只有降低暴露面：摘下时断开连接、配合 WiFi 必要条件限定在家或公司。安全要求高的话，别用这套方案。

## 二、原理

### 2.1 为什么 shell 能向锁屏注入

Android 的锁屏是安全窗口，普通应用和辅助功能都无法注入事件。但 `adb shell` 与 Shizuku 的运行身份是 `uid 2000(shell)`，持有 `INJECT_EVENTS`，可以向安全窗口注入按键。这是整套方案唯一的基础。

### 2.2 两分钟可行性自测

不同机型拦截程度不同，建议先确认：

1. 锁屏并上滑，调出 PIN 键盘。
2. 执行 `adb shell input keyevent 8`（数字 1）。
3. 观察右下角按钮，正常会从「返回」变成「删除」。

变了说明注入有效；没变说明该机型堵死了这条路，后面的内容不必再看。

### 2.3 一次解锁的时序

```
屏幕点亮 → power_screen_state 事件
  ├─ 防抖 2 秒
  ├─ 读在线缓存 wu.present        40～110ms
  ├─ 判断是否锁屏                  10～50ms
  ├─ wm dismiss-keyguard           约 50ms
  ├─ 等待 0.1 秒                   100ms
  ├─ input text <PIN>              150～220ms
  └─ 复核焦点，成功即刻返回
       失败 → 慢路径：换开门方式、确认键盘、重新注入
```

顺利时只做一次锁屏判断、一次唤键盘、一次注入。

## 三、安装与部署

### 3.1 安装包

```
watch-unlock-1.0.apk    76.7 KB
包名   com.watchunlock.app
版本   1.0（versionCode 1）
最低   Android 8.0（minSdk 26）
目标   Android 14（targetSdk 34）
签名   v1 + v2 + v3
```

体积小是没有引入 AndroidX 和其它依赖，界面全部用代码构建，细节在第七节。

签名校验有个细节：`apksigner verify` 默认按 minSdk 26 检查，此时 JAR 签名（v1）会显示 false，因为 Android 8 以上只认 v2/v3；加上 `--min-sdk-version 23` 复验，v1/v2/v3 三项才都是 true。两种结果都不影响安装。

### 3.2 安装

点开安装即可，需要允许「安装未知应用」。用 adb：

```sh
adb install -r watch-unlock-1.0.apk
```

小米 / 红米用户可能遇到 `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`。这不是包的问题，是 MIUI 的「USB 安装」开关没开：

1. 设置 → 开发者选项 → 打开「USB 安装」；
2. 或者绕开安装会话：

```sh
adb push watch-unlock-1.0.apk /data/local/tmp/wu.apk
adb shell pm install -r /data/local/tmp/wu.apk
```

### 3.3 首次启动的两个授权

1. **Shizuku 权限**：弹框选「始终允许」。注意 `pm grant` 对它无效，Shizuku 走自己的授权列表，只能在应用里点。
2. **附近的设备**：Android 12 起监听蓝牙广播需要这个权限。拒绝也能用，只是退化成每次亮屏现查，慢 0.3～0.8 秒。

### 3.4 从旧版升级

本版使用正式签名，与之前的调试包不兼容，`adb install -r` 会报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE`。需要先卸载：

```sh
adb uninstall com.watchunlock.app
adb install watch-unlock-1.0.apk
```

卸载会清空勾选、PIN 和 Shizuku 授权，装完要重新配置。

## 四、首次配置

界面从上到下是四块。

### 4.1 状态卡

显示守护是否运行、Shizuku 是否就绪、当前解锁条件，以及一行实时状态，例如 `在线 1/2 · 已锁屏 · WiFi 15`。

显示「尚未部署」说明配置目录被清理过，点下面的「部署并启用」恢复。

### 4.2 蓝牙设备

列出系统里所有已配对设备，每行是名称、MAC、已连接/未连接，右侧一个开关。

新配对的设备默认不勾选。这是刻意的：首次安装若全勾上，耳机、笔记本、车机都会变成解锁条件。

勾选后会自动写配置并重启守护，不需要重新输 PIN。

HyperOS 用户可能遇到「所有设备都显示未连接」。原因是系统把 `dumpsys` 里的 MAC 脱敏成 `XX:XX:XX:XX:EE:FF`，只保留末两段。1.0 已兼容：界面同时接受完整 MAC、设备名、MAC 末五位三种匹配方式。

### 4.3 解锁条件

- **多设备模式**：关闭时任一启用设备在线即可；打开时要求全部在线。
- **WiFi 作为必要条件**：打开后必须同时连在已启用的 SSID 上。关闭时不查 WiFi，省掉每次 310～360ms。
- **WiFi 列表**：每个 SSID 一个开关，「添加当前 WiFi」直接抓当前网络。

### 4.4 操作区

| 按钮 | 作用 |
| --- | --- |
| PIN 输入 | 填锁屏密码，纯数字 |
| 部署并启用 | 把守护推到 `/sdcard/watch-unlock` 并启动 |
| 重启守护 / 停止守护 | 字面意思 |
| 查看日志 | 跳到独立日志页 |
| 一键清理残留 | 停进程、删配置目录，保留勾选 |
| 性能基准 | 实测各类命令耗时 |
| 授权 Shizuku | 重新触发授权弹框 |

### 4.5 语言切换

标题右侧有个胶囊按钮，点一次按「自动 → 中文 → English」循环，切换后界面立即刷新，不需要重启。

- **自动**：系统语言是中文就显示中文，其它一律英文。
- 手动选定的语言会记住，装到另一台设备时保持。
- 通知栏的标题和正文也会跟着切换。

部分系统（如 LineageOS）的「应用语言」入口不一定可用，以应用内这个按钮为准。

配置顺序建议：输 PIN → 勾设备 → 部署并启用 → 熄屏再亮屏验证一次。

## 五、条件模型

### 5.1 多设备语义

配置里 `TARGETS` 每条是 `启用|MAC|名称`，`WATCH_MODE` 取 `any` 或 `all`。未勾选的设备完全不参与判定，日志里写成 `bt 1/2`。

三种典型用法：

1. 只勾手表：戴表解锁，摘表要密码。
2. 勾手表 + 耳机：出门只听歌也能解锁。
3. 勾两件且开 `all`：两件都在才解锁，安全高一档，但更容易失效。

### 5.2 WiFi 的两种角色

1. **仅作条件**：打开「WiFi 作为必要条件」后，必须连在已启用 SSID 上才解锁。
2. **额外触发源**：守护同时监听 WiFi 连接事件，连上可信 SSID 且屏幕亮着、仍锁屏时，补一次解锁。

SSID 区分大小写，改过 WiFi 名字要同步改列表。

### 5.3 暂停

三个按钮写入 `pause_until` 时间戳，守护每轮事件前重读，立即生效，脚本或手机重启都不丢。暂停期间通知栏显示剩余时间。

## 六、实现细节

### 6.1 在线状态改为事件驱动

早期版本靠后台定时查询蓝牙状态，一次 300～800ms，且空闲时也在唤醒 CPU。

现在的做法是缓存加事件：

| 时刻 | 谁触发 | 作用 |
| --- | --- | --- |
| 守护启动 | 守护自己 | 冷启动先有一份初值 |
| 设备连接或断开 | 应用收到 ACL 广播 | 状态真变了，刷新缓存并登记「在监听」 |
| 蓝牙开关变化 | 应用收到适配器状态广播 | 同上 |
| 每次息屏 | 应用收到息屏广播 | 趁没人看时把缓存刷热 |
| 应用启动 | 应用主动调 `--present track` | 补初值并登记 |
| 应用无法监听 | 调 `--untrack` | 撤销登记，退化为现查 |

亮屏时只读一次文件。信任缓存的条件是 `online=yes` 且 `track=1` 且应用进程还在。三者缺一就现查一次——宁可慢，也不拿过期缓存去解锁。

### 6.2 开门方式固定为 dismiss-keyguard

早期靠 `dumpsys window policy` 里的字段判断要不要上滑。LineageOS 上根本没有这个字段，于是每次白花约 350ms 发一个上滑动画。

现在固定用 `wm dismiss-keyguard`，只有失败后的慢路径才回退上滑。顺带解决了一个隐蔽问题：音乐类应用接管锁屏时，上滑事件会被它吞掉，密码键盘根本不出现。

### 6.3 确认策略

注入后用 `dumpsys window | grep mCurrentFocus` 复核，每次约 80ms，最多 12 次，成功立即返回。

不用 `KeyguardServiceDelegate` 的 `showing=`，实测不可靠：解锁成功且已亮屏时仍可能报 `true`。`mCurrentFocus` 多花一次 dumpsys，但结论稳定。

### 6.4 保护机制

1. 屏幕事件防抖 2 秒，WiFi 事件 6 秒。
2. 连续失败 3 次进入 10 分钟冷却。
3. 未唤醒不注入，未锁屏不注入。
4. 单实例保护：锁文件加 `ps` 精确匹配，只认 `sh <路径>wu-daemon.sh` 这一形态，排除 `sh -c` 包装和 `--present`、`--check` 这类辅助调用。

第四条是踩过坑才加的。两个守护同时跑会抢着注入，日志里出现「一个 unlocked、另一个 slow」，旧版还会因为上滑回退在正常使用时把界面往下带。

## 七、从脚本到应用：一次重构的取舍

这一节讲为什么要做 APK，以及构建时想了什么。如果只想用，可以跳过。

### 7.1 起点是一堆 shell 脚本

最早的需求只有一件事：手表在时自动解锁。方案很直接——一个 `.sh` 文件，Shizuku 身份执行，监听亮屏事件，注入 PIN。前后不到一百行，第一天就跑通了。

那时候的部署方式是：把脚本推到手机，用 MT 管理器执行，参数写在命令里。能用，但只对写脚本的人友好。

### 7.2 用久了暴露的问题

问题不是功能不够，而是每加一个需求，脚本方案的成本就涨一截。

1. **配置变成手工活。** 从单设备变成多设备后，配置从几个变量变成结构化列表，手改容易错。最典型的一次是把分隔符打成了中文逗号，整串被当成一个设备名，表现是「完全不触发」，排查了半天。
2. **临时操作要记命令。** 想暂停一小时、想重启守护、想看状态，都得记参数。
3. **出问题只能看日志。** 没有界面，状态、在线数、冷却剩余全靠 `--check` 输出。
4. **分享门槛太高。** 让别人用要走：装 Shizuku → 装文件管理器 → 找到目录 → 执行脚本 → 输入参数。任何一步都会劝退。

到这一步其实有两条路：继续把脚本做得更聪明，或者在外面包一层界面。

### 7.3 决定：脚本做核，应用做壳

最后选的不是二选一，而是分工。

**守护逻辑留在 shell。** 注入按键、读 `dumpsys`、判断锁屏、处理事件，这些在 shell 里最直接：改一行就能测，日志一眼能看懂，出问题可以直接在终端里复现。搬进 Java 反而要处理进程模型、权限和线程，收益为零。

**应用只做四件事：**

1. 提供配置界面，把勾选结果写进配置文件；
2. 监听蓝牙和 WiFi 广播，状态一变就通知守护刷新缓存；
3. 亮屏时确认守护还活着，不在就拉起；
4. 提供日志、状态、清理这些运维入口。

换句话说，应用不参与解锁，它只是让守护变得可控。

### 7.4 构建上的几个决定

**不用 Gradle 和 AndroidX。** 这台机器上原本只有 JDK 和 build-tools，没有任何构建框架。与其为了一个几百 KB 的应用引入 Gradle 的依赖树，不如直接调五个工具：`aapt2` 编译资源、`javac` 编译、`d8` 转 dex、`zipalign` 对齐、`apksigner` 签名。代价是没有依赖管理，好处是构建十秒完成、包体 72KB、每一步都可控。

**界面全用代码写。** 控件加起来几十个，写布局 XML 再编译资源并不会更快，反而多一层资源编译。纯代码构建省掉了半条工具链，也方便按状态动态生成列表——设备列表、WiFi 列表本来就是变长的。

**守护脚本放进 assets。** 安装后第一次部署时把 `wu-daemon.sh` 推到 `/sdcard/watch-unlock/`，之后升级脚本只需要替换资产文件。这样脚本仍是唯一真相源，改逻辑不用重新理解 Java。

**所有优化只针对热路径。** 从亮屏到输入完成只有几百毫秒，界面漂不漂亮、设置页有几层都不影响它。所以优化集中在减少进程启动次数、用缓存代替查询、把慢操作挪出热路径这三件事上。

**失败必须看得见。** 日志页、`--check`、`--bench` 三个入口是刻意留的。解锁这类功能，出问题时用户只会说「没反应」，没有数据就只能猜。留好这三个入口，排查时间从半天缩到十分钟。

### 7.5 回头看

如果一开始就做应用，前两天会花在搭环境和调界面，而脚本方案第一天就能验证「注入锁屏是否可行」这个核心问题。

反过来，如果一直停在脚本，这套东西永远只有自己能用。

所以顺序是对的：先用脚本把可行性跑通、把坑踩完，再包一层壳解决易用性。中途也试过用 MacroDroid 承担界面，但配置和日志都没地方放，最后放弃。

## 八、实测数据

### 8.1 两台机器

| 项 | xaga（LineageOS 24 / Android 17） | 小米 15（HyperOS 3 / Android 16） |
| --- | --- | --- |
| 守护 UID | 0（Shizuku 以 root 运行） | 2000（Shizuku 以 shell 运行） |
| 连续轮次 | 6/6 成功 | 6/6 成功 |
| `total` | 960 / 970 / 1000 / 1010 / 1030 / 1070ms | 550 / 570 / 660 / 670 / 700 / 730ms |
| `lock` | 30～50ms | 10～40ms |
| `presence`（缓存命中） | 40～110ms | 40～50ms |
| `inject` | 180～220ms | 150～180ms |

修复设备识别问题后补测过一轮：小米 15 连续 3 次 700 / 700 / 850ms，xaga 2 次 1000 / 1010ms，与上表一致，没有回归。

### 8.2 时间都去哪了

```
timing: lock=40ms presence=50ms inject=210ms
result: unlocked (total=990ms)
```

脚本侧只占 250～300ms，剩下是 SystemUI 接收 PIN、校验、播动画的时间。小米 15 上注入后约 476ms 焦点才离开锁屏，基本是那台机器的极限。

### 8.3 0.5 秒为什么没做到

想再快只有三条路：缩短注入后的固定等待（有丢 PIN 风险）、常驻注入器省掉 `input` 的 50～60ms 进程启动、监听 keyguard 广播代替 `dumpsys`。

前两条收益 50～100ms，第三条要改系统侧。0.5 秒以内需要直接解除 keyguard，那已经不属于注入方案了。

## 九、常见问题

**设备显示「未连接」，勾了也没用**

HyperOS / Android 13+ 会把 MAC 脱敏。1.0 已能按完整 MAC、设备名、MAC 末五位匹配。仍然不行就检查设备是否真的连着——有些耳机放进充电盒就断连。

**状态卡提示「尚未部署」**

配置目录被清理过。点一次「部署并启用」，勾选不会丢。

**日志里同一秒出现 unlocked 又出现 slow / skip**

两个守护在抢。1.0 有单实例保护，启动时发现已有实例会直接退出并写 `already running`。开发时手工删过 `/data/local/tmp/wu.lock` 的话，用「重启守护」或「一键清理残留」收尾。

**用着用着界面突然「下滑」一下**

旧版残留的守护在走上滑回退，`input swipe` 会把界面往下带。点一次「一键清理残留」，1.0 本身不会再出现。

**RSSI 阈值开了但日志说系统没暴露**

部分 ROM 的 `dumpsys bluetooth_manager` 不带 RSSI。此时门槛自动失效、只留日志，不会把功能卡死。

**应用要一直开着吗**

不用。解锁全在 shell 守护里，应用只负责传状态和刷新通知。应用被清掉时，守护在亮屏那一刻会自己现查蓝牙，功能正常，只是慢 0.3～0.8 秒。

**注入后 600ms 还没解锁，是不是失败了**

不一定。keyguard 退场动画期间焦点仍停在锁屏窗口，会多查几次；12 次（约 2 秒）都没解锁才判失败。这段等待只在失败时支付。

**为什么还要查一次锁屏状态**

不能省。屏幕处于「已解锁但刚亮」时（来电、充电常亮、刚解锁），省掉这一步会把 PIN 直接打进当前应用，比慢更糟。

**重启手机后要手动开吗**

Shizuku 本身需要重新激活。Shizuku 一恢复，应用会在下次亮屏时发现守护不在并自动拉起。

**界面是英文，怎么改回中文**

点标题右侧的胶囊按钮循环切换，或者把它切到「自动」跟随系统语言。切换是即时的，不用重启应用。

**怎么彻底停掉**

应用里点「停止守护」；连配置一起清就点「一键清理残留」。命令行等价：

```sh
adb shell sh /sdcard/watch-unlock/wu-stop.sh
```

## 十、安全说明

这套方案的本质是在特定条件下替用户输入锁屏密码，客观上降低了设备安全性，使用前需要接受这一点。

1. 密码以明文形式存在 `/sdcard/watch-unlock/config.conf` 与应用私有存储中。Android 11 之后普通应用无法随意读取共享存储，但文件管理器可以查看。
2. 摘下手表后必须确认锁屏恢复正常，这是部署后第一时间要验证的内容。
3. 账号凭证（微信、支付宝）不受影响，锁屏 PIN 只解屏幕。
4. 不要把 APK 连同自己的配置文件一起发给别人。

## 十一、边界

1. **只支持 PIN 码锁屏。** 图案和混合密码不支持，因为注入走 `input text`。画图案要用 `input swipe`，风险高且不稳，刻意不做。
2. **无法判断设备是否戴在身上。** 见 1.4。
3. **依赖 Shizuku。** 非 root 设备重启后要重新激活，这是唯一绕不过的日常维护点。
4. **首次解锁会慢。** 缓存为空时走现查，比平时多 0.3～0.8 秒。
5. **设备同名会互串。** 两台设备重名时按名称匹配可能错配，建议改其中一个的名字，或改用 MAC。

## 十二、日志与排查

### 11.1 日志页

主界面点「查看日志」进入独立页面：深色、等宽字体、2.5 秒自动刷新，可刷新、复制、清空。日志超过 1MB 自动轮转为 `.old`。

正常一次：

```
present(cache): bt 1/1
timing: lock=40ms presence=50ms inject=210ms
result: unlocked (total=990ms)
```

`present:` 后面没有 `(cache)` 说明这轮走了现查，`presence` 会变成 300～800ms。常见原因：应用被清掉、没启动、没给「附近的设备」权限。

### 11.2 状态自检

```sh
adb shell sh /sdcard/watch-unlock/wu-daemon.sh --check
```

输出启用数、在线数、锁屏状态、WiFi、冷却与暂停剩余，以及 `bt_check_ms`。

### 11.3 性能基准

应用里点「性能基准」，各命令测三次：

```
bluetooth_manager : 30/50/60ms
window policy     : 10/40/30ms
power             : 20/70/100ms
wifi              : 310/360/340ms
uiautomator dump  : 3320/2220/2210ms
input (spawn)     : 50/50/60ms
```

如果 `window policy` 或 `input` 也很慢，说明瓶颈在系统侧，脚本已经到底。

配置项含义：

| 键 | 说明 |
| --- | --- |

| `WATCH_MODE` | `any` 任一在线，`all` 全部在线 |

| `WIFI_REQUIRED` | 1 表示 WiFi 为必要条件 |
| `RSSI_MIN` | 距离门槛，系统不暴露 RSSI 时无效 |
| `DEBOUNCE` / `MAX_FAILS` / `COOLDOWN` | 防抖、失败阈值、冷却秒数 |
