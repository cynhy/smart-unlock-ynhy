# 手表联动解锁的两个改动：input text 注入与解锁复核

适用环境：小米 15（24129PN74C），HyperOS 3（V816），Android 16，未 root，Shizuku 13.6。
本文只讲 2026-11-03 这次的两处改动，整套方案的完整说明见《酷安教程-手表联动解锁.md》。
效果：锁屏密码改为 `input text` 一次性提交；解锁成功后不再因为退场动画误判而把 DEL 和密码打进桌面。

---

## 一、改了什么

### 1.1 注入方式：keyevent 换成 input text

原实现把 PIN 换算成键码，逐个发 `input keyevent`：

```sh
input keyevent 9 12 15 10 13 16
```

现在配置里直接存密码原文，一次提交：

```sh
input text "$PIN_TEXT"
```

两者底层都是向 `InputManager` 注入按键事件，权限要求相同，仍然必须是 shell 身份（adb shell 或 Shizuku）。

### 1.2 解锁复核：修掉一个会把按键打进桌面的竞态

原来的流程是注入后固定 `sleep 0.7`，再查是否还锁屏。密码其实已经输对、但 keyguard 还在播退场动画时，`mIsShowing` 仍是 `true`，于是被判定为失败，进入重试分支：此时键盘已经消失，`DEL × 8 + PIN` 会直接打进刚解锁的桌面。

现在的流程是：

1. 注入后轮询等待解锁，最多 3 秒；
2. 仍未解锁时，先用 `uiautomator dump` 确认密码键盘还在；
3. 键盘不在就放弃重试，不计数，也不执行任何按键。

### 1.3 改动范围

| 文件 | 改动 |
| --- | --- |
| `phone/deploy.sh` | 配置增加 `PIN_TEXT`；注入改 `input text`；新增 `wait_unlocked()` 与 `keypad_present()`；重写 `do_unlock()` 的重试分支 |
| `手机端部署包/deploy.sh` | 同步 |
| `手表自动解锁-手机端部署包.zip` | 重打 |
| 教程、说明、交接说明 | 同步描述 |

## 二、问题为什么存在

### 2.1 失败时序

```
亮屏 → 检查通过 → dismiss-keyguard → 注入 PIN
                                        │
                              密码校验通过（系统开始退场动画）
                                        │
                              mIsShowing 仍为 true
                                        │
                          sleep 0.7 后查询 → 误判"还锁着"
                                        │
                         DEL × 8 + PIN → 打进桌面
```

关键在于：**"密码正确"和"锁屏状态变成 false"不是同一时刻**。前者在系统内部立即发生，后者要等窗口动画和 SystemUI 状态切换完成。

### 2.2 改成 input text 并没有解决它

`input text` 只是把六位数字打包成一组按键事件，提交速度更快，甚至会让"密码通过"发生得更早，从而更容易撞上 0.7 秒这个检查点。所以这次必须单独处理复核逻辑。

### 2.3 实测时间窗口

在小米 15 上连续采样 `dumpsys window policy` 的 `mIsShowing`：

| 注入后 | mIsShowing | 当前焦点 |
| --- | --- | --- |
| 第 1 到 6 次采样 | true | NotificationShade |
| 第 7 次采样 | false | com.miui.home Launcher |

单次 `dumpsys` 约 0.1 秒，翻转发生在注入后约 0.6 到 0.9 秒之间，正好压在原来的 0.7 秒检查点上。这解释了为什么日志里有时正常、有时会走重试。

同时做了错误密码对照：输入 `111111` 后连续 8 次采样，`mIsShowing` 始终为 true，焦点始终是 `NotificationShade`。说明解锁确实由注入完成，不是人脸或信任设备生效。

## 三、原理

### 3.1 input text 能进安全锁屏

`input text` 的实现是 `KeyCharacterMap.getEvents()` 把字符串拆成 `KeyEvent` 序列，再走 `InputManager.injectInputEvent`。与 `input keyevent` 走的是同一条注入通道，因此同样具备 `INJECT_EVENTS` 权限、同样能到达安全窗口。

限制与之前一致：必须是 uid 2000（shell），普通应用无解；键盘仍会短暂出现。

### 3.2 为什么不能只看一次 locked()

`locked()` 读的是窗口状态，包含动画过程。密码通过后，SystemUI 需要完成 bouncer 消失、壁纸切换、焦点交还，这段时间内窗口状态还没翻篇。任何"固定等待 + 查一次"的写法都有概率误判。

正确做法是把"查一次"换成"等它变"，并且给等待设上限。

### 3.3 为什么用键盘存在性做最终闸门

窗口状态会滞后，但界面结构不会骗人：bouncer 消失后，`keyguard_pin_view` / `pinEntry` 就不再出现在 UI 树里。

实测两种状态的 `uiautomator dump`：

| 状态 | keyguard_pin_view | pinEntry |
| --- | --- | --- |
| 已解锁（桌面） | 0 | 0 |
| 锁屏且键盘展开 | 1 | 1 |

所以只要在重试前确认键盘还在，即使真的误判，按键也只会落在密码键盘上，不会落到桌面。这是最后一道保险。

## 四、实现

### 4.1 配置

`/sdcard/watch-unlock/config.conf` 新增一行：

```
PIN_TEXT="<锁屏PIN>"
PIN_KEYS="9 12 15 10 13 16"
```

`PIN_TEXT` 是注入用的原文，`PIN_KEYS` 保留给 `--check` 输出。部署时由 `-p` 自动生成，不需要手填。

### 4.2 等待解锁

```sh
wait_unlocked() {
  n=0
  while [ $n -lt 12 ]; do
    locked || return 0
    sleep 0.25; n=$((n+1))
  done
  return 1
}
```

每 0.25 秒查一次，最多 3 秒。正常解锁在 1 秒内返回，只有真失败才会跑满。

### 4.3 键盘存在性

```sh
keypad_present() {
  uiautomator dump /data/local/tmp/wu.ui >/dev/null 2>&1 || return 1
  grep -qE 'keyguard_pin_view|/pinEntry' /data/local/tmp/wu.ui 2>/dev/null
}
```

同时匹配 MIUI 的 `keyguard_pin_view` 和 AOSP 的 `pinEntry`。`uiautomator dump` 失败时返回 1（当作键盘不在），宁可放弃重试。

### 4.4 新的 do_unlock 流程

```
dismiss-keyguard
input text PIN
  ├─ wait_unlocked 成功 → result: unlocked
  └─ 3 秒仍未解锁
       ├─ keypad_present 为否
       │    ├─ 再等 0.8 秒，成功 → result: unlocked (late)
       │    ├─ 换备用路径唤键盘，成功 → result: unlocked (late)
       │    └─ 键盘仍不在 → abort: no keypad, refuse to inject（不计数）
       └─ keypad_present 为是
            └─ DEL × 8 → input text PIN → wait_unlocked
                 ├─ 成功 → result: unlocked (retry)
                 └─ 失败 → result: still locked（计一次失败）
```

只有在"确认键盘还在"之后才会执行 DEL 和重输，这是与旧版最大的区别。

### 4.5 日志对照

| 日志 | 含义 |
| --- | --- |
| `result: unlocked` | 主路径成功 |
| `result: unlocked (late)` | 主路径其实成功，只是复核晚了一点 |
| `retry: keypad gone, re-check` | 复核时键盘已消失，先重新确认状态 |
| `abort: no keypad, refuse to inject` | 键盘不在，放弃重试，不计失败 |
| `retry: clear and inject again` | 键盘仍在，清空后重输 |
| `result: unlocked (retry)` | 重试成功 |
| `result: still locked` | 真的失败，计一次 |

## 五、部署与升级

电脑端：

```sh
adb -s <设备序列号> push phone/deploy.sh /data/local/tmp/
adb -s <设备序列号> shell "sh /data/local/tmp/deploy.sh -p <密码> -w 'OPPO Watch X 4CD8,MOONDROP Pudding'"
```

手机端：

```sh
sh /sdcard/watch-unlock-pkg/一键部署.sh
```

部署会重写 `config.conf` 并重启守护进程，旧配置里的 `PIN_KEYS` 不需要手工迁移。

## 六、验证清单

**第一步，自检**

```sh
adb shell sh /sdcard/watch-unlock/wu-daemon.sh --check
```

`watch_online` 应为 yes，`pin_keys` 与密码一致。

**第二步，连续亮屏**

熄屏后点亮，重复三次。日志应出现三组 `inject` 与 `result: unlocked`，间隔 1 到 2 秒：

```
17:19:19 inject: watch online + locked (mode=dismiss)
17:19:20 result: unlocked
```

本次实测 4 次（含一次守护启动时的补解锁）全部成功，未出现 `retry` 或 `abort`。

**第三步，观察复核是否生效**

若日志出现 `result: unlocked (late)`，说明退场动画比预期慢，复核逻辑接住了；只要是这个结果，桌面不会被打进任何按键。

**第四步，摘表测试（必做）**

摘下手表并断开连接，点亮屏幕，确认仍然需要输入密码。

## 七、常见问题

**日志出现 `abort: no keypad, refuse to inject`**

键盘不在，脚本主动放弃重试。通常代表上一次注入其实已经成功，只是状态查询滞后。这种情况不计失败次数，也不会往桌面打字。

**重试仍然是同一个密码，有意义吗**

主要意义是兜住"键盘没弹出来"和"输入被吞掉"两类问题，而不是修正密码错误。密码错时重试会失败并计入冷却，这是预期行为。

**为什么等待上限是 3 秒**

实测正常解锁在 1 秒内完成，3 秒足够覆盖动画较慢的机型。再长会让失败路径的延迟变得明显。

**`uiautomator dump` 会不会很慢**

只在失败路径调用一次，约 0.4 秒。成功路径完全不走这段代码。

**明文密码存在配置里安全吗**

不安全，只是可用性取舍。`config.conf` 里现在同时有 `PIN_TEXT` 和 `PIN_KEYS`，文件管理器可以查看。介意的话自行加密存放，或在用完后删除配置。

---

## 八、限制

1. AOSP / LineageOS 的上滑路径未在本次改动中实测，`input text` 与复核逻辑对两条路径通用，但上滑路径依赖真实手势，建议在目标机型上重新跑一遍第六节。
2. `input text` 仍要求键盘实际出现并接收事件，无法后台静默提交。
3. 佩戴状态依旧无法判断，本次改动不涉及该短板。
