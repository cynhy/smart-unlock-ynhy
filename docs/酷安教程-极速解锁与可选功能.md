# 蓝牙设备解锁 2.0：把亮屏解锁压进 1 秒 + 可选功能

适用环境：Redmi 22041216C（xaga），LineageOS（Android 17，userdebug）；另一台验证机为小米 15 / HyperOS 3 / Android 16。
目标：从屏幕点亮到 PIN 输完、进入桌面，目标 0.5 秒，最差不超过 1 秒；同时把后台占用压下来，并把 Shizuku 托管做成可选项。

> 说明：2.0 已在两台真机上跑通：xaga（LineageOS 24 / Android 17）**960~1070ms**，小米 15（HyperOS 3 / Android 16）**550~840ms**（实测见 2.6 与第八节）。
> 2.0 的功能名称从「手表解锁」改为「蓝牙设备解锁」：条件不再是一块手表，而是任意已勾选的蓝牙设备（可多选）。

---

## 一、上一版为什么慢

上一版一次解锁的耗时大致是这样堆起来的（约 3 秒）：

| 阶段 | 动作 | 典型耗时 |
| --- | --- | --- |
| 1 | `dumpsys power` 轮询 Awake（最多 20 次 ×0.1s） | 0~2000ms |
| 2 | `dumpsys window policy` 判锁屏 | 100~200ms |
| 3 | `dumpsys bluetooth_manager` 判设备在线 | 300~800ms |
| 4 | `wm dismiss-keyguard` + `sleep 0.3` | 300~400ms |
| 5 | `uiautomator dump` 查键盘是否在 | 500~1500ms（实测 2.2~3.3s） |
| 6 | `input text` 注入 | 150~300ms |
| 7 | 每 0.25s 轮询一次 `dumpsys window policy` 确认解锁 | 250~750ms |

真正必要的只有第 2、6 步，其余都是「保险」。保险越多越稳，但每一层都在加时间。

## 二、这一版怎么改

### 2.1 设备在线状态：从轮询改成事件驱动

先说结论：**解锁动作本来就是事件驱动的**——守护只监听 `power_screen_state` 那一条日志，亮屏才动手，从来没有定时轮询。之前慢的原因是「手表在不在」这个状态靠后台定时刷新，现在也改成事件驱动了。

新增 `/data/local/tmp/wu.present` 缓存：

```
ts=... online=yes/no src=bt/wifi hit=1/2 track=1
```

它只在下面几个时刻重算，**没有任何定时刷新**：

| 时刻 | 谁触发 | 为什么 |
| --- | --- | --- |
| 守护启动 | 守护自己 | 冷启动先有一份初值 |
| 手表/耳机连接或断开 | 应用收到 `ACTION_ACL_CONNECTED / DISCONNECTED` | 状态真的变了，并登记「我在监听」 |
| 蓝牙开关变化 | 应用收到 `ACTION_STATE_CHANGED` | 同上 |
| 每次息屏 | 应用收到 `ACTION_SCREEN_OFF` | 趁没人看的时候先把缓存刷热，下次亮屏 0ms（不改变登记状态） |
| 应用启动/注册成功 | 应用主动调 `--present track` | 补一份初值并登记「我在监听」 |
| 应用无法监听 | 应用主动调 `--untrack` | 撤销登记，退化为亮屏现查 |

亮屏时热路径只做一次文件 `read`。判定能否信任缓存的条件是 `online=yes` **且** `track=1` **且** `pidof com.watchunlock.app` 有结果：

- 应用活着且已登记监听 → 蓝牙事件一个都不会漏，缓存必然准确，**直接信任，0ms**；
- 应用被杀 / 没启动 / 没给「附近的设备」权限 → 现查一次（300~800ms），宁可慢也不拿过期缓存去解锁。

应用侧对应地把「每 60 秒问一次状态」的定时器删了，改成监听亮屏 / 解锁完成 / 蓝牙变化三类广播。

### 2.2 热路径只留三步

```
屏幕点亮 → power_screen_state [1,...]
  ├─ 防抖 2 秒（长防抖 6 秒只留给 WiFi 事件）
  ├─ 读 wu.present 缓存       ← 50ms
  ├─ dumpsys window policy    ← 确认还在锁屏（安全底线，不能省）
  ├─ wm dismiss-keyguard      ← 拉起 PIN 键盘，不发上滑动画
  └─ input text PIN           ← 注入
```

防抖参数是这轮的关键修复：上一版所有事件统一用 6 秒防抖，**锁屏后 6 秒内再亮屏会被直接 `continue` 跳过，连日志都不写**——这就是"经常不执行"的根因。现在屏幕事件只防 2 秒内的重复触发，6 秒长防抖只给 WiFi 扫描这类高频事件。

开门方式也不再探测。原逻辑靠 `dumpsys window policy | grep mIsShowing=` 判断要不要上滑，而 LineageOS 24 根本没有这个字段 → 被判成"需要上滑"，白花 ~350ms 发一个上滑动画。现在固定用 `wm dismiss-keyguard`，只有在失败后的慢路径里才回退上滑。

`uiautomator dump` 从热路径彻底移除，只在失败后的慢路径里用。

### 2.3 失败才走慢路径

注入后用 `locked_fast` 复核最多 12 次（只看 `dumpsys window | grep mCurrentFocus`，实测 80ms/次，加 0.1s 间隔约 180ms/次，共约 2 秒）：

- 已解锁 → 直接写 `result: unlocked`，结束；
- 仍锁屏 → 进慢路径：切备用开门方式 → 确认键盘在 → 重新注入 → 动态 DEL 重试 → 失败计数与冷却。

这里不用 `KeyguardServiceDelegate` 的 `showing=`：在本 ROM 上它并不可靠（解锁成功且已亮屏时仍会报 `true`，息屏时也时真时假）。`mCurrentFocus` 虽然多花一次 dumpsys，但结论稳定。

也就是说，**顺利时只花一次 `dumpsys window policy` + 一次 `dismiss` + 一次 `input`**；不顺时才付保险的钱。

### 2.4 关键改动清单

| 改动 | 作用 |
| --- | --- |
| `wu.present` 事件驱动缓存 | 省掉 300~800ms 的蓝牙 dumpsys，且空闲时零后台唤醒 |
| 去掉 `uiautomator dump` | 省掉 0.5~1.5s |
| `open_fast`：只 dismiss，`FAST_SETTLE=0.1` | 省掉 0.3~0.6s 固定等待 |
| 固定 `wm dismiss-keyguard`，不再探测开门方式 | 省掉误判时多发的 ~350ms 上滑 |
| 解锁确认改为 `locked_fast` 12×0.1s（成功即返回） | 成功路径不等待；只在失败时多等 ~2s，避免误进慢路径 |
| 屏幕事件防抖 6s → 2s | 修复「锁屏后 6 秒内亮屏被吞」，不再漏执行 |
| 状态文件用 `read` 读首行，不再 `head/grep` | 每次事件少两个进程 |
| 毫秒计时用 `/proc/uptime` | 诊断无额外开销 |
| `POCKET_GUARD=0` 默认关闭显示状态检查 | 再省一次 dumpsys；需要防误触时在选项里打开 |

### 2.5 日志里怎么看到耗时

每次解锁会多两行：

```
result: unlocked (total=990ms)
timing: lock=40ms presence=50ms inject=210ms
```

`total` 是从事件触发到确认解锁的总时间，`inject` 里包含 `dismiss + input` 两次进程启动。要再压，就看这三段谁大。

### 2.6 真机实测：时间都花在哪

设备：Redmi 22041216C（xaga）/ LineageOS 24 / Android 17（SDK 37）。`--bench` 连跑三次取区间：

| 操作 | 实测 | 说明 |
| --- | --- | --- |
| `wm dismiss-keyguard` | 50ms | 热路径开门 |
| `input text <锁屏PIN>` | 59ms | 注入 6 位 PIN |
| `input` 进程启动本身 | 50~60ms | 每次调 `input` 的固定开销 |
| `dumpsys window policy` | 10~40ms | 锁屏状态（慢路径用） |
| `dumpsys window \| grep mCurrentFocus` | ~80ms | `locked_fast` 确认解锁 |
| `dumpsys bluetooth_manager` | 30~60ms | 现查设备在线 |
| `dumpsys wifi` | 310~360ms | 现查 WiFi，所以不能进热路径 |
| `uiautomator dump` | 2220~3320ms | 已彻底移出热路径 |

热路径实际日志：

```
present(cache): bt 1/1
timing: lock=40ms presence=50ms inject=210ms
result: unlocked (total=990ms)
```

**结论**：守护自己能控制的部分只有 ~270ms（lock 40 + presence 50 + inject 180），剩下大部分是 SystemUI 接收 PIN、校验、播解锁动画的时间，脚本再怎么优化也压不掉。

小米 15（HyperOS 3 / Android 16）实测更短，连续 6 轮：

```
result: unlocked (total=670ms)   timing: lock=20ms presence=50ms inject=170ms
result: unlocked (total=550ms)   timing: lock=20ms presence=50ms inject=170ms
result: unlocked (total=660ms)   timing: lock=20ms presence=50ms inject=160ms
result: unlocked (total=570ms)   timing: lock=20ms presence=50ms inject=180ms
```

SystemUI 侧只要 ~300ms（焦点在注入后 476ms 就离开 keyguard），所以 550ms 已经是这台机器的极限附近；0.5 秒仍然差一点点，1 秒内两台都达成。想真正进 0.5 秒只能改 Android 侧锁屏（例如 LSPosed 直接解除 keyguard），不在本方案范围内。

## 三、2.0 的界面与条件模型

### 3.0 界面结构

```
蓝牙设备解锁
├─ 状态卡        守护运行中 / Shizuku / 解锁条件 / 当前（在线 1/2 · 未锁屏 · WiFi 15）
├─ 蓝牙设备      每个已配对设备一行：名称 + MAC + 已连接/未连接 + 右侧「启用」开关
├─ 解锁条件      多设备模式（所有已启用设备必须同时在线）
│                WiFi 作为必要条件（开启后 WiFi 必须命中已启用的 SSID）
│                WiFi 列表（每项一个开关 + 删除，「添加当前 WiFi」）
├─ 操作          PIN 输入 / 部署并启用 / 重启守护 / 停止守护 / 查看日志 / 一键清理残留 / 性能基准 / 授权 Shizuku
└─ 高级          Shizuku 托管运行 / RSSI 阈值 / 暂停 15m · 1h · 4h / 恢复
```

几个要点：

- **设备逐个启用**：新配对的设备默认**不勾选**（2.0.1 起），避免首次安装把耳机、笔记本一起算进条件；勾选后自动写配置并重启守护，不用重新输 PIN。
- **WiFi 同理**：每个 SSID 一行一个开关，只有启用过的 SSID 才算数；「添加当前 WiFi」直接抓当前 SSID，也可以手动加。
- **日志是二级页面**：主界面的「查看日志」跳转到独立的深色日志页（自动刷新开关 + 刷新 / 复制 / 清空），主界面只放按钮，不再占屏幕。
- **一键清理残留**：停守护与前台服务、结束旧版守护/logcat 监听、删除 `/sdcard/watch-unlock` 与 `/data/local/tmp/wu.*`；设备与 WiFi 的勾选保留，清理后可一键重新部署。

### 3.1 多设备模式（AND 语义）

- 关闭（默认）：**已启用的设备中任意一个在线**即可解锁（`WATCH_MODE=any`）；
- 打开：**所有已启用的设备必须同时在线**（`WATCH_MODE=all`），安全提升一档。

2.0 的判定改成「启用清单」：`TARGETS` 每条是 `启用|MAC|名称`，`watch_online()` 按名称/MAC 逐个匹配，日志里写 `bt 2/2`。只对勾选的设备生效，未勾选的一律不参与。

### 3.4' WiFi 作为必要条件

「WiFi 作为必要条件」打开后（`WIFI_REQUIRED=1`），WiFi 从「额外的解锁触发源」变成**必要条件**：

- 蓝牙条件（按 3.1 判定）**且** 当前 SSID 命中任一已启用的 WiFi，才允许解锁；
- 不满足时日志写 `skip: 解锁条件不满足…`，`wu.present` 里是 `online=no src=no-wifi`；
- 关闭时完全不查 WiFi（省掉每次 310~360ms 的 `dumpsys wifi`）。

### 3.2 临时暂停

应用里三个按钮：15 分钟 / 1 小时 / 4 小时，另有「恢复自动解锁」。

实现是往状态文件写 `pause_until` 时间戳，守护每轮事件前都会重读，**立刻生效，且脚本重启/手机重启都不会丢**。暂停期间通知栏会显示剩余分钟数。

### 3.3 RSSI 距离门槛

`RSSI_MIN=-70` 之类。数值越接近 0 要求越近。系统没暴露 RSSI 时**只记日志、不拦截**，避免直接锁死功能。开启后热路径会强制实时查询，不再吃缓存（会慢一点，这是取舍）。

### 3.4 WiFi 列表与连接触发

每个 SSID 一行、独立开关（配置里是 `WIFI_LIST`，每条 `启用|SSID`）。行为分两种：

1. **只作为条件**（打开「WiFi 作为必要条件」）：必须连在已启用的 SSID 上才解锁，见 3.4'；
2. **额外触发源**：守护同时监听 `wifi_network_state_changed`，连上已启用的 WiFi 且屏幕亮着、还锁着时，会补一次解锁并记 `trigger: 连上可信 WiFi xxx`。

SSID 区分大小写，改过 WiFi 名字要同步改这里。带引号的 SSID（如 `"15"`）已做解析兼容。

### 3.5 运行方式：独立进程 / Shizuku 托管

| 模式 | 说明 | 适合 |
| --- | --- | --- |
| `detached`（默认） | `nohup` 起独立进程，脱离 Shizuku 进程树；守护被系统清掉后，应用在下一次亮屏时自动拉起 | 日常使用，最稳 |
| `shizuku` | 守护作为 Shizuku 的子进程持有，随 Shizuku 生命周期存活/退出 | 调试、想让进程归属清晰 |

勾「Shizuku 托管运行」写入 `RUN_MODE=shizuku` 并重启守护。注意托管模式下 Shizuku 一挂，守护立刻停；应用会尝试重新拉起，但如果 Shizuku 本身没启动，只能等它恢复。

## 四、后台占用

| 项 | 上一版 | 现在 |
| --- | --- | --- |
| 在线状态刷新 | 后台每 60 秒查一次蓝牙 | **完全事件驱动**，只有连接/断开/开关/息屏才重算，空闲时 0 次 |
| 应用看护 | 固定 20 秒一次 Shizuku 调用 | **事件驱动**：只在亮屏 / 解锁完成 / 蓝牙变化时读一次状态 |
| 热路径 dumpsys | 1 次 | 1 次（默认） |
| 日志 | 每次解锁 3~5 行 | 2~3 行，超 1MB 轮转 |
| 后台子进程 | 1 个刷新循环 | 0 个，除了常驻的 logcat 监听 |

也就是说：**亮屏时才干活，其余时间守护只剩一个 `logcat` 挂在那里等事件**，不再有周期性唤醒。

## 五、怎么验证

### 5.1 应用内「性能基准」

点一下会输出每类命令的真实耗时（各测 3 次）：

```
bluetooth_manager : 30/50/60ms
window policy     : 10/40/30ms
power             : 20/70/100ms
wifi              : 310/360/340ms
uiautomator dump  : 3320/2220/2210ms
input (spawn)     : 50/50/60ms
```

如果 `window policy` 或 `input` 也很慢，说明瓶颈在系统侧，脚本层面已经压到极限（下一步只能做常驻注入器，风险较大，暂不做）。

### 5.2 日志对照

应用里点「查看日志」进入二级页（自动刷新）；命令行也可以直接看：

```
$ adb shell tail -n 20 /sdcard/watch-unlock/wu.log
```

正常一次：

```
present(cache): bt 1/1
timing: lock=40ms presence=50ms inject=210ms
result: unlocked (total=990ms)
```

日志里出现 `present:`（没有 `(cache)`）说明这一轮走了现查，`presence` 会变成 300~800ms。常见原因三种：应用被杀、应用没启动、没给「附近的设备」权限。想确认是哪种：

```
$ adb shell pidof com.watchunlock.app        # 有输出 = 应用活着
$ adb shell cat /data/local/tmp/wu.present   # track=1 才算已登记监听
```

### 5.3 状态自检

```
$ adb shell sh /sdcard/watch-unlock/wu-daemon.sh --check
```

会给出匹配设备、在线数、锁屏/亮屏、RSSI、WiFi、冷却与暂停剩余，以及 `bt_check_ms`（蓝牙检查的真实耗时）。

## 六、常见问题

**Q：为什么还要查一次锁屏状态，不能省吗？**
不能。省掉后一旦屏幕是「已解锁但刚亮」的状态（来电、充电常亮、信任设备），PIN 会直接打进当前应用，比慢更糟。

**Q：注入后 600ms 还没解锁，是不是失败了？**
不一定。keyguard 退场动画期间焦点仍停在锁屏窗口上，所以会多查几次；12 次（约 2 秒）都没解锁才判定失败并走慢路径。这段等待只在失败分支付钱，成功一次就立刻返回。

**Q：日志里同一秒出现「unlocked」又出现「slow / skip」？**
这是**两个守护在抢**。守护 2.0 已加单实例保护（锁文件 + `ps` 兜底，只认 `sh <路径>wu-daemon.sh` 这一形态），启动时发现已有实例会直接退出并写 `already running`。如果你在开发时手动删过 `/data/local/tmp/wu.lock`，务必用应用里的「重启守护 / 一键清理残留」收尾，不要再手工起第二个。

**Q：RSSI 打开了但日志写「系统未暴露 RSSI」？**
部分 ROM 的 `dumpsys bluetooth_manager` 不带 RSSI 字段，此时门槛自动失效，只留日志，不会把功能卡死。

**Q：应用要一直开着吗？关了会不会不解锁？**

不用开着。解锁全在 shell 守护里，应用只做两件事：把「手表连上了」这件事告诉守护、以及在亮屏时刷新通知。应用被清掉时，守护发现 `pidof` 查不到它，会在亮屏那一刻自己现查蓝牙——功能仍然正常，只是慢 0.3~0.8 秒。

**Q：为什么要给「附近的设备」权限？**

Android 12 起，监听蓝牙连接/断开广播需要 `BLUETOOTH_CONNECT`（界面上的「附近的设备」）。给了才能做到零轮询；拒绝也没关系，会自动退化为每次亮屏现查，只是慢一点，不会有功能缺失。

**Q：托管模式重启手机后会自动恢复吗？**
Shizuku 本身要在重启后重新激活（无线调试配对或 root 启动）。Shizuku 一恢复，应用在下一次亮屏时会发现守护不在并自动拉起，不用手动点。

**Q：怎么彻底停掉 / 怎么清干净？**
应用里点「停止守护」，或「一键清理残留」（后者会连旧版守护、logcat 监听、`/sdcard/watch-unlock`、`/data/local/tmp/wu.*` 一起删除，但保留勾选）。命令行等价：`adb shell sh /sdcard/watch-unlock/wu-stop.sh`。

**Q：HyperOS / Android 13+ 上设备一直显示「未连接」，勾了也没法用？**
这是系统把 `dumpsys bluetooth_manager` 里的 MAC 脱敏成 `XX:XX:XX:XX:EE:FF`（只保留最后两段）。2.0.2 起界面同时接受「完整 MAC / 设备名 / MAC 末 5 位」，`A2dpStateMachine`、`BassClientStateMachine` 等段落里 `state=Connected` 的都能认出来；守护端本来就是按名称匹配，不受影响。如果你看到「尚未部署（点下面的「部署并启用」）」，那是配置目录被清理过，点一次部署即可。

**Q：手机上明明没在用，为什么会突然「下滑」一下？**
那是旧版（1.x）残留的第二个守护在走「上滑开门」回退：`input swipe` 会把当前界面往下带。2.0 的处理是：① 守护只认单实例（`ps` 兜底检查），② 「一键清理残留」会杀掉所有旧版 `wu-daemon.sh` 与 `logcat -b events`，③ 慢路径只在确认真锁屏时才动作。清完之后两台设备均未再复现。

## 七、本轮还没做的

1. **常驻注入器**：用 `app_process` 起一个常驻 Java 进程，通过 FIFO 接受注入命令，能再省掉 `input` 的 ~50~60ms 启动开销。需要额外 dex 与进程管理，未在真机验证前不并入主线。
2. **再压确认段**：`locked_fast` 每次 `dumpsys window` 约 80ms；若改成监听 keyguard 状态广播，可能再省 ~100ms。已在真机上按 `--bench` 结果定下当前参数（`FAST_SETTLE=0.1`、12×0.1s 成功即返回）。
3. **开机自启链路**：`BootReceiver` 已在清单里，但重启后 Shizuku 不在，只能等 Shizuku 恢复后由应用在下次亮屏时拉起。

## 八、两台设备实测对比

| 项 | xaga（LineageOS 24 / Android 17） | 小米 15（HyperOS 3 / Android 16） |
| --- | --- | --- |
| 守护 UID | 0（Shizuku 以 root 运行） | 2000（Shizuku 以 shell 运行） |
| 连续轮次 | 6/6 成功 | 6/6 成功 |
| `total` | **960 / 970 / 1030 / 1070 / 1000 / 970ms** | **670 / 670 / 550 / 660 / 570 / 730ms** |
| `lock` | 30~50ms | 20~40ms |
| `presence`（缓存命中） | 40~110ms | 40~50ms |
| `inject`（dismiss + input） | 180~200ms | 150~180ms |
| 解锁后焦点切换 | 注入后约 900~1000ms | 注入后约 476ms |

**结论**：两台都稳定在 1 秒内；小米 15 已经到 550ms，剩余几乎全是 SystemUI 侧。刷机/换 ROM 后请重新跑一遍 `sh /sdcard/watch-unlock/wu-daemon.sh --check` 和 5 轮息屏/亮屏。

### 8.1 小米 15 安装注意（MIUI/HyperOS）

`adb install` 会报 `INSTALL_FAILED_USER_RESTRICTED: Install canceled by user`，这是 MIUI 的「USB 安装」开关没开，不是包的问题。两个办法：

1. 设置 → 开发者选项 → 打开「USB安装」（本机开关位置在「调试」分组里）；
2. 或者绕开安装会话：`adb push watch-unlock-2.0.apk /data/local/tmp/wu.apk && adb shell pm install -r /data/local/tmp/wu.apk`。

装完首次打开会弹两个框：Shizuku 授权（选「始终允许」）和「附近的设备」权限（选「始终允许」）。
