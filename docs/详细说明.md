## 1. 这是什么

一个 Android 小工具：**当指定的蓝牙设备（手表、耳机、手环等）在线时，手机每次亮屏就自动输入锁屏 PIN 并解除锁屏**。

解决的问题：戴着手表/耳机时，手机明明就在手边，却每次亮屏都要手动划一下、输密码。

核心特点：

- **不需要 root**（默认走 Shizuku），也不需要电脑常驻；
- **解锁动作不依赖应用进程**：部署后在后台跑一个 shell 守护脚本，应用被划掉、被系统杀掉都不影响解锁；
- **三档授权可选**：Shizuku / Root / 内置无线调试（手机自己当 ADB 客户端）；
- **事件驱动，几乎不耗电**：监听系统 `logcat` 的亮屏/断网事件，不做轮询。

> 本项目会向系统注入锁屏密码。请先读 [安全与隐私](#16-安全与隐私)，确认风险后再使用。

## 2. 适用平台与硬性限制

| 项目 | 要求 |
| --- | --- |
| 最低系统 | **Android 8.0（API 26）** |
| 内置无线调试 | **Android 11 及以上**（系统「无线调试」功能起始版本） |
| 锁屏方式 | **PIN 码（纯数字）**，不支持图案/密码/指纹单独解锁 |
| 权限 | 通知、附近设备（Android 12+ 蓝牙）、电池优化白名单（可选，因为核心不依赖其） |
| 实测环境 | Android 12 / 13 / 14 / 16（LineageOS24.0、HyperOS3，鸿蒙4.2） |

### 为什么最低是 8.0

不是解锁原理的限制，而是当前实现用了 Android 8.0 才有的通知模型：

- `NotificationChannel`（API 26）
- `new Notification.Builder(context, channelId)`（API 26）
- `startForegroundService()`（API 26）

低于 8.0 时这些类/方法不存在，程序在建通知或起前台服务时会直接崩溃（`NoClassDefFoundError` / `NoSuchMethodError`）。同时 APK 声明了 `minSdk 26`，**7.1 及以下连安装都会被系统拒绝**。

需要说明的是：解锁链路本身（`sh` + `logcat -b events` + `wm dismiss-keyguard` + `input text`）在更老的系统上原理可行，`wm dismiss-keyguard` 约从 5.0 就有。若要支持 5.0～7.1，需要把前台服务换成 `startService`、去掉通知渠道、改用旧版 `Notification.Builder`，并重新处理 6/7 的运行时权限——属于「可以适配，但当前没有做也没有实测」---

## 3. 工作原理

### 3.1 一句话流程

```
蓝牙设备在线 / 连上可信 Wi-Fi
        │
        ▼
屏幕点亮（系统 logcat events 事件）
        │
        ▼
wu-daemon.sh（以 shell uid 2000 常驻，事件驱动）
        │  读 /sdcard/watch-unlock/config.conf
        │  判断：目标设备在线？Wi-Fi 条件？暂停/冷却？已锁屏？
        ▼
wm dismiss-keyguard  →  input text <PIN>  →  （可选）音乐锁屏返回
```

### 3.2 进程模型

| 进程 | 身份 | 作用 | 生命周期 |
| --- | --- | --- | --- |
| `com.watchunlock.app` | 普通应用 uid | 界面、配置下发、状态展示、蓝牙广播监听 | 随应用/系统，可被杀 |
| `wu-daemon.sh` | shell（uid 2000） | 监听亮屏事件、执行解锁 | 部署后常驻，**不依赖应用存活** |
| `logcat -b events` | shell 子进程 | 向守护脚本提供系统事件流 | 随守护，退出后 1 秒自动重启 |

守护用 `nohup sh wu-daemon.sh &` 启动，父 shell 退出后挂到 `init` 下，因此：

- 划掉最近任务、系统强停应用 → 解锁照常；
- Shizuku 被杀/关闭 → 守护仍在（默认 `RUN_MODE=detached`；若切成 `RUN_MODE=shizuku` 托管模式则随 Shizuku 结束）；
- **手机重启 → 守护消失**，需要授权引擎重新拉起（应用前台服务有 60 秒看门狗，但前提是授权已就绪）。

### 3.3 一次解锁的时序

1. 守护收到 `power_screen_state [1,...]`（亮屏）或 `wifi_network_state_changed`；
2. 息屏事件只用于清零防抖，不触发；
3. 读状态文件，检查 `status=disabled`、暂停、失败冷却；
4. 检查条件：目标设备在线（任一/全部）、Wi-Fi 必要条件、RSSI 下限、SIM 防呆；
5. 抢跨进程锁 `wu.unlock.d`，1.5 秒内已注入过则跳过；
6. `wm dismiss-keyguard` 把 PIN 界面拉起，`input text <PIN>` 注入；失败时退回 uiautomator 定位输入框的方案；
7. 成功后（可选）执行音乐锁屏返回：按包名 `am start`，或向右滑动；
8. 失败累计 3 次后进入 600 秒冷却，避免疯狂重试。

### 3.4 蓝牙在线判定

- 守护启动时先用 `presence_refresh` 刷一次在线缓存（`/data/local/tmp/wu.present`）；
- 之后由应用监听蓝牙连接/断开广播，调用 `wu-daemon.sh --present track` 实时维护；
- 如果应用无法监听蓝牙（没给「附近设备」权限），会调用 `--untrack` 撤销「可信缓存」标记，亮屏时改为现查（慢一点，但不会拿过期结论解锁）；
- 3.3.3 起，**部署与重启都会清掉这份缓存**，避免上一轮的结论残留。

## 4. 三档授权

三种方式执行的是**同一套守护脚本**，区别只在「谁给 shell 身份」。设置页可随时切换，但**切换后必须重新点「部署并启用」**。

| 方式 | 需要什么 | 稳定性 | 适合谁 | 主要限制 |
| --- | --- | --- | --- | --- |
| **Shizuku**（默认） | 安装并运行 Shizuku，在本应用点「请求授权」 | 最稳 | 大多数用户 | Shizuku 被系统回收后需重新启动；建议加入电池白名单 |
| **Root** | 设备已 root，`su` 弹窗放行 | 稳定（取决于 su 实现） | 已 root 的用户 | 开发者选项 Root access 需为「Apps and ADB」；部分 ROM 的 su 只对 adb 开放 |
| **内置无线调试** | 开发者选项打开「无线调试」，用配对码配对一次 | 中等 | 不想装 Shizuku 也不能 root | 需 Android 11+；重启后无线调试自动关闭、端口会变，需重新配对/连接 |

### 4.1 Shizuku

1. 安装 [Shizuku](https://shizuku.rikka.app/) 并启动（无线调试或 root 方式启动 Shizuku 均可）；
2. 本应用 → 设置 → 授权方式 → Shizuku → 「请求授权」；
3. 回到主页 → 「部署并启用」。

Shizuku 本身也依赖 ADB/root 启动，但它是常驻服务，配置一次即可；部分系统会回收它，建议把 Shizuku 和本应用都加入电池优化白名单。

### 4.2 Root

1. 开发者选项 → Root access 设为「Apps and ADB」（不同 ROM 名称略有差异）；
2. 本应用 → 设置 → 授权方式 → Root；
3. 首次部署时会弹 `su` 授权框，选「允许」；
4. 回到主页 → 「部署并启用」。

无需 Magisk 模块。若提示 `Root unavailable`，说明 `su` 没有对本应用放行，或设备实际未 root。

### 4.3 内置无线调试（不依赖 Shizuku）

应用内置 [Kadb](https://github.com/flyfishxu/Kadb) 作为 ADB 客户端，手机自己连本机的无线调试端口（默认 `127.0.0.1`）。

配对步骤（两个端口不是同一个数字）：

1. 开发者选项 → 打开「无线调试」；
2. 在「无线调试」主页面找到 **IP 地址和端口**，把端口填到应用的「连接端口」；
3. 点「使用配对码配对设备」，弹窗里显示 **另一个端口** 和 6 位配对码，分别填到「配对端口」和「配对码」；
4. **保持配对弹窗打开**，点「配对」；成功后点「连接测试」；
5. 重启手机后无线调试会自动关闭，需要重新打开并再配对一次。

注意：

- 配对弹窗关闭后配对端口立即失效；
- 连接失败时，到开发者选项把「无线调试」关一次再打开，然后重新配对；
- 系统页面里才会显示配对码，本应用读不到。

### 4.4 授权方式对比：什么时候还需要它

| 场景 | 是否需要授权引擎 |
| --- | --- |
| 日常亮屏解锁（守护已在跑） | **不需要** |
| 首次部署 / 重新部署 | 需要 |
| 改设置后套用配置 | 需要 |
| 暂停 / 恢复 / 一键清理 / 读状态 | 需要 |
| 蓝牙断开后刷新在线缓存 | 需要（否则沿用旧缓存） |
| 守护被杀后 60 秒看门狗拉起 | 需要 |
| **手机重启后恢复守护** | **需要**（Shizuku 未开机自启时必须重新授权） |

## 5. 功能详解

### 5.1 蓝牙目标设备

- 主页「蓝牙设备」卡片会自动读取系统里**已配对**的设备（需要「附近的设备」权限），点「重新扫描」可刷新；
- 新发现的设备默认**不启用**，避免首次安装时把所有耳机/手表都算进「任一在线」；
- 列表每条可单独勾选启用/停用，只有勾选的设备参与判定；
- 模式二选一：
  - **任一在线**（默认）：列表中任意一个启用的设备在线即满足条件；
  - **全部在线**（「多设备模式」开启）：所有启用的设备都必须在线。
- 支持 RSSI 下限（`RSSI_MIN`），信号太弱时视为不在线，避免隔墙误触发。

### 5.2 Wi-Fi 条件

两个独立开关，可组合：

| 开关 | 含义 |
| --- | --- |
| Wi-Fi 可解锁 | 连上列表中任一启用的 SSID 即可触发解锁（蓝牙不要求） |
| Wi-Fi 为必要条件 | 蓝牙在线之外，还必须连着指定 SSID 才解锁 |

限制：**只能添加「当前已连接」的 Wi-Fi**，不支持手动输入 SSID（应用读不到未连接网络的凭据信息）。需要添加某个网络时，先连上它，再点「添加当前 WiFi」。

### 5.3 锁屏 PIN

- 4～16 位纯数字；
- 保存在应用私有 `SharedPreferences` 与 `/sdcard/watch-unlock/config.conf`；
- 注入方式以 `input text` 为主，必要时用 `input keyevent` 逐位补输；
- **不要**用图案/混合密码，脚本无法可靠注入。

### 5.4 SIM 卡 PIN 防呆

- 默认关闭；
- 开启后，解锁前多查一次 SIM 锁定状态：若 SIM 处于 PIN 锁定界面，**拒绝注入手机 PIN**，避免把手机锁屏密码打到 SIM 上导致锁卡；
- 代价是多一次状态检查，解锁速度与成功率会略降。

### 5.5 暂停与恢复

主页提供「暂停 15 分钟 / 1 小时 / 4 小时」与自定义秒数，以及「恢复」。

- 暂停写入状态文件，守护进程不退出，只是跳过解锁；
- 适合临时把手机脱离身边，比如交给别人使用时、或不需要自动解锁的时段。

### 5.6 震动反馈

- 设置页有总开关，默认开启；
- 点击按钮、切换开关时轻微震动（`VIRTUAL_KEY`，忽略系统「触摸震动」总开关）；
- 关闭后应用内所有交互不再震动，不影响解锁本身。

### 5.7 音乐锁屏返回

锁屏是音乐界面时，输完 PIN 常常退不出去。提供两种方式，可单独或同时开启：

| 方式 | 行为 | 备注 |
| --- | --- | --- |
| 按包名打开应用 | 解锁后 `am start` 打开指定包名的主界面 | **同时开启时优先这一种**；包名填错会退回右滑（若已开启） |
| 向右滑动 | 解锁后执行一次右滑手势 | 部分 ROM 的音乐锁屏会截获手势，此时改用打开应用 |

包名必须完整（如 `com.netease.cloudmusic`），不是应用名称。

### 5.8 公告栏（三级页面）

包含：

- 当前版本与签名说明（正式包 / 测试包不能互装）；
- **重要提醒**（改动后重新部署、部署会清什么不会清什么、3.3.3 的缓存修复、切换授权需重新部署）；
- **更新日志**（按版本汇总，含每个版本的 bug 修复）；
- 使用注意（授权、端口、Wi-Fi、SIM、音乐返回、后台限制等）；
- 开源组件鸣谢：蓝字可点开查看许可协议。

### 5.9 日志页

- 查看 `/sdcard/watch-unlock/wu.log`（守护日志）；
- 支持一键复制、清空；
- 日志超过 1 MB 自动轮转为 `wu.log.old`；
- 部署失败的详细原因也会写进日志页可见位置。

### 5.10 一键清理残留

入口：主页「一键清理残留」（危险色按钮，二次确认）。

执行内容：

- 停守护、杀所有 `wu-daemon.sh` 与 `logcat -b events` 残留进程；
- 删除 `/sdcard/watch-unlock/`（脚本、配置、日志）；
- 删除 `/data/local/tmp/wu.*`（锁、状态、缓存、临时文件）。

**保留**应用内的设备勾选与 Wi-Fi 列表，方便清理后重新部署。清理后必须重新部署才能恢复解锁。

### 5.11 内置 ADB 控制台

入口：主页「无线调试」卡片（或设置 → 无线调试）。

- 顶部可直接输入一条 `adb shell` 命令并执行，回显退出码与输出；
- 使用前必须先完成无线调试的配对与连接；
- 页面内含操作步骤、连接参数（主机/连接端口/配对端口/配对码）、配对/连接测试/断开按钮，以及「打开无线调试设置」快捷跳转。

> 设计初衷：既然内置了 ADB 客户端，就顺便把它当命令控制台用，不必再连电脑。

### 5.12 语言

- 默认跟随系统；
- 设置页可强制中文 / English（`I18n` 双语文案，资源侧含 `values` 与 `values-en`）。

## 6. 首次使用流程

1. 安装 APK（正式签名或测试签名，详见 [第 12 节](#12-安装升级与签名)）。
2. 打开应用，按提示授予 **通知**、**附近设备** 权限。
3. 进入 **设置 → 授权方式**，选择 Shizuku / Root / 无线调试，并完成对应授权（见 [第 4 节](#4-三档授权)）。
4. 回到主页，在「蓝牙设备」卡片里勾选目标设备（先让手表/耳机与手机配对；列表为空时点「重新扫描」）；如需要，再点「添加当前 WiFi」。
5. 输入锁屏 PIN（4～16 位数字）。
6. 按需调整：任一/全部在线、Wi-Fi 解锁/必要条件、RSSI 下限、SIM 防呆、音乐锁屏返回、震动。
7. 点 **「部署并启用」**，状态变为「运行中」即生效。
8. 锁屏后点亮屏幕验证：应自动解锁。
9. **之后每次改动任何选项，都回到主页再点一次「部署并启用」**（原因见下一节）。
10. 建议把本应用（以及 Shizuku）加入电池优化白名单，允许自启动/后台运行。

## 7. 为什么改完设置要重新部署

设置项变化会「立即重写配置并重启守护」，但重新部署做的是更彻底的一套动作：

| 动作 | 改设置后自动重启 | 点「部署并启用」 |
| --- | --- | --- |
| 重写 `config.conf` | 是 | 是 |
| 杀旧守护 + 旧 `logcat` 监听 | 是 | 是 |
| 清 `wu.daemon.d` / `wu.unlock.d` 锁目录 | 是 | 是 |
| 清 `wu.lock` / `wu.shot` | 是 | 是 |
| 清 `wu.state`（失败计数/冷却） | 否 | 是 |
| **清 `wu.present` / `wu.cm` / `wu.kw`（在线缓存）** | **3.3.3 起是** | **3.3.3 起是** |
| 重写守护脚本 `wu-daemon.sh` / `wu-stop.sh` | 否 | 是 |
| 保留你的设置、设备勾选、日志 | 是 | 是 |

3.3.3 修复的具体问题：旧版部署/重启时没有删除 `wu.present`，它会保留「上一轮哪个设备在线」的结论。设备其实已经断开，缓存还写着在线，亮屏就会误解锁，这种情况理论只会发生在刚断开连接后快速重新进行一次解锁时。现在部署与重启都会清掉它。

**结论：为了稳定，改动任何选项后请回到主页重新点「部署并启用」。**

## 8. 配置文件与运行时文件

### 8.1 `/sdcard/watch-unlock/`

| 文件 | 说明 |
| --- | --- |
| `config.conf` | 主配置，由应用部署时写入（见下表） |
| `options.conf` | 运行模式等可选覆盖；不存在时部署会写入 `RUN_MODE="detached"` |
| `wu-daemon.sh` | 守护脚本（随 APK assets 下发） |
| `wu-stop.sh` | 停止脚本：只杀守护与 logcat，排除自身与父进程 |
| `wu.log` | 运行日志；超过 1 MB 轮转为 `wu.log.old` |

### 8.2 `config.conf` 字段

| 字段 | 含义 | 默认/示例 |

## 9. 守护脚本的命令接口

`wu-daemon.sh` 除常驻模式外，还支持一次性调用：

| 命令 | 作用 | 谁调用 |
| --- | --- | --- |
| `sh wu-daemon.sh` | 启动常驻监听 | 部署 / 看门狗 |
| `--unlock` | 立即执行一次解锁（不依赖常驻守护是否活着） | 应用收到亮屏广播 |
| `--present [track]` | 刷新蓝牙在线缓存；带 `track` 表示应用正在监听广播，缓存可长期信任 | 应用 |
| `--untrack` | 撤销「可信缓存」标记，之后亮屏现查 | 应用（无法监听蓝牙时） |
| `--pause <秒>` | 暂停解锁，写入状态 | 主页暂停按钮 |
| `--resume` | 取消暂停 | 主页恢复按钮 |
| `--check` | 打印诊断信息（目标数、匹配 MAC、在线状态、RSSI、Wi-Fi、锁屏状态、PIN 长度、冷却/暂停剩余） | 手动排查 |
| `--bench` | 连续 3 次测量关键命令耗时（dumpsys / uiautomator / input spawn） | 性能排查 |

`--check` 输出里的 `status` / `reason` 是最直接的排查依据；例如 `disabled` 表示 PIN 校验失败被禁用，需要核对密码后重新部署。

## 10. 解锁决策逻辑

按顺序判断，任一不满足就跳过：

1. `status != disabled`；
2. 不在暂停期、不在失败冷却期；
3. 屏幕处于点亮且已锁屏；
4. 蓝牙条件满足（任一/全部在线，且 RSSI 不低于下限）；
5. 若开启「Wi-Fi 必要条件」，当前 SSID 必须在启用列表内；
6. 若开启「SIM 防呆」，SIM 未处于 PIN 锁定界面；
7. 通过跨进程互斥（`wu.unlock.d`）；
8. 距上次注入超过 1.5 秒。

失败处理：

- 每次失败累加计数；
- 连续 `MAX_FAILS=3` 次失败进入 `COOLDOWN=600` 秒冷却，期间不再尝试；
- 冷却结束自动恢复；也可在应用里「恢复」或重新部署重置状态。

防抖：

- 亮屏固定 2 秒（避免「锁屏后立刻又亮屏」被吞）；
- Wi-Fi 事件 6 秒（可配）；
- 息屏事件只清零防抖计时，不触发解锁。

## 11. 资源占用实测

测试环境：小米 15（HyperOS），版本 1.0（守护架构与 3.x 相同）。测量方法：`ps` + `/proc`、`batterystats`、60 秒 CPU tick 采样。

| 指标 | 结果 |
| --- | --- |
| 后台进程数 | 3（`sh` 守护 + `logcat` + 管道子 `sh`） |
| 常驻内存（RSS） | 约 **9.2 MB**（3.4 MB + 4.4 MB + 1.4 MB） |
| 60 秒 CPU | **0 tick**（折合 < 0.017% / 单核） |
| 应用进程 | 未运行时 **0** |
| batterystats 累计 | 19 小时 1 分 34 秒 ≈ **0.14%** |
| Alarm 唤醒 | 无 |
| 长期 wakelock | 无 |

原因：守护只做「阻塞读 logcat」，没有定时器、没有轮询；蓝牙在线状态由应用广播维护，守护自身不查蓝牙。

## 14. 常见问题

**Q1：状态显示「授权服务已断开 / Shizuku 未运行」**
Shizuku 被系统回收。重新打开 Shizuku 并保持后台常驻，把 Shizuku 与本应用加入电池优化白名单（也可以不这样做，可以选择让守护成为独立进程，毕竟只有当更改选项的时候才需要授权）。

**Q2：部署成功但亮屏不解锁**
按顺序排查：
1. 主页状态是否为「运行中」；
2. `--check` 里 `watch_online` 是否 `yes`、`locked` 是否 `yes`；
3. 目标设备是否在「已启用」列表里；
4. 是否处于暂停/冷却期；
5. 是否刚改过设置却没重新部署（请重新点「部署并启用」）。

**Q3：解锁后停在音乐锁屏**
设置 → 音乐锁屏返回：填写音乐应用包名（如 `com.netease.cloudmusic`），或开启向右滑动。部分 ROM 会截获右滑手势，优先用打开应用。

**Q4：Wi-Fi 列表里没有想加的网络**
只能添加「当前已连接」的 Wi-Fi，先连上目标网络，再点「添加当前 WiFi」。

**Q5：无线调试提示 not configured / 连接失败**
先在「无线调试」页完成配对与连接；配对端口与连接端口不是同一个数字；重启后需重新配对。仍失败时到开发者选项关闭再打开「无线调试」。

**Q6：换授权方式后不生效**
切换档位必须重新点「部署并启用」，必要时重启应用。

**Q7：重启手机后不解锁**
守护不会跨重启存活。开机后应用会尝试自动拉起，但需要授权就绪：Shizuku 要能开机自启，无线调试要重新打开并连接，Root 要能放行 `su`。

**Q8：提示 PIN 必须是 4～16 位数字**
确认锁屏用的是纯数字 PIN，且长度在 4～16 位之间。

**Q9：`state=disabled`**
PIN 校验多次失败后守护会自我禁用。核对 PIN 后重新部署即可。

**Q10：想彻底重置**
先「一键清理残留」，再重新部署；如果仍异常，卸载重装（会清空所有设置）。

## 15. 已知限制

- **重启后需要授权引擎**重新拉起守护，无法做到真正「一次部署永久生效」；
- **无线调试**依赖系统端口与配对状态，重启后失效；
- **音乐锁屏返回**在不同 ROM 上差异较大，右滑可能被系统接管；
- **Root 档**在部分 ROM 上 `su` 只对 adb 开放，应用拿不到；
- **只能 PIN 解锁**，不支持图案/混合密码；
- **HyperOS / ColorOS** 等需允许自启动与后台运行，否则 Shizuku 会被回收；
- **系统省电极严**时亮屏事件可能延迟，建议加入白名单；
- **8.0 以下无法安装**（见 [第 2 节](#2-适用平台与硬性限制)）。

## 16. 安全与隐私

- 应用会向系统注入锁屏 PIN。**不要在共享设备或不受信任的设备上使用。**
- PIN 保存在应用私有目录的 `SharedPreferences` 与 `/sdcard/watch-unlock/config.conf`；
  - 应用私有目录其他应用读不到；
  - `/sdcard` 上的配置文件在无 root 时其他应用也读不到（受作用域存储限制），但**拿到 shell/root 的人可以读**。
- 应用不联网上传任何数据,完全的本地应用；无线调试仅连接 `127.0.0.1` 本机端口。
- 建议开启「SIM PIN 防呆」，避免误把手机 PIN 注入 SIM；
- 建议按需使用暂停功能，避免在不需要时自动解锁；
- 日志中不记录 PIN 明文，只记录 PIN 长度与状态。

关键设计：

- 三档授权被抽象成同一条执行接口，上层逻辑不关心底层用哪一档；
- 配置下发与解锁执行完全分离：应用只写配置，解锁全部在守护里；
- 所有运行时状态用文件 + 目录锁表达，不依赖数据库或常驻 socket；
- 事件驱动，无轮询、无 Alarm、无 wakelock。

## 19. 与原生和厂商方案的对比

对比对象：① Google 原生 **Extend Unlock**（旧名 Smart Lock 可信设备）；② 国内厂商自研的「智能解锁 / 蓝牙设备解锁」（小米、华为、OPPO、vivo 等）。

本应用不走系统 `TrustAgent` 可信代理 API，而是用 **shell（uid 2000）身份注入 PIN**，因此绕开了两套系统方案的硬限制。

### 19.1 总览

| 维度 | Google Extend Unlock | 厂商智能解锁 | 本应用 |
| --- | --- | --- | --- |
| 已锁屏时能否自动解锁 | **不能**，只维持已解锁状态（最长 4 小时） | 能（但是有一些仅限自家穿戴） | **能**，锁屏熄屏后亮屏即注入 PIN |
| 可用设备范围 | 任意已配对蓝牙（受系统与 GMS 限制） | **可能只认自家手表/手环** | **任意已配对蓝牙**：耳机、音箱、车载、第三方手环均可 |
| 是否依赖 GMS | 依赖，国行无 GMS 机型通常没有入口 | 不依赖，但绑定自家 ROM | **不依赖**，国行 ROM 完整可用 |
| Wi-Fi 条件 | 无 | 基本无 | **有**：Wi-Fi 可独立解锁，也可作为蓝牙的必要条件 |
| 多设备逻辑 | 无 | 无（通常单个设备） | **任一在线 / 全部在线** 两种模式 |
| RSSI（距离）限制 | 无 | 部分有 | 有，低于阈值视为不在线 |
| 授权方式 | 系统内置 | 系统内置 | Shizuku / Root / 内置无线调试 |
| 有效期 | 约 4 小时后重新校验 | 由厂商策略决定 | 无有效期，直到进程被结束或重启 |
| 可观测性 | 几乎没有用户可用的日志 | 几乎没有 | 完整日志：触发条件、耗时、成功/失败原因、`--check`、`--bench` |
| 兼容系统 | 依赖 GMS 与 Google 策略 | 绑定自家 ROM 版本 | Android 8.0+理论上都可以，在测试的时候鸿蒙4.2 ,EMUI,HyperOS , LineageOS 等均可 |
| 主要短板 | 锁屏后不生效、无 Wi-Fi/多设备、国行常缺失 | 生态锁定、功能固定、ROM 强绑定 | 仅数字 PIN、PIN 明文落盘、重启后需重新授权 |

### 19.2 相比 Google 原生（Extend Unlock / Smart Lock）

原生的硬限制：

1. **Android 10 起，可信设备不再解锁已锁屏的手机**，只在你已解锁后「维持不锁」，有效期最长约 4 小时；手动锁屏后即使手表连着，也要自己输密码。
2. **依赖 GMS**：国行无 Google 服务的机型通常没有该入口，部分国内 ROM 直接隐藏。
3. **没有 Wi-Fi 条件，也没有多设备组合逻辑**。

本应用：

- 真正在**锁屏状态下**自动解锁：熄屏锁屏后，只要蓝牙/Wi-Fi 条件满足，亮屏即自动输入 PIN；不受 Android 10 可信代理规则约束，**没有 4 小时有效期**；
- 不依赖 GMS；
- 条件模型更细：蓝牙多设备、RSSI 下限、Wi-Fi 独立解锁或必要条件、SIM 防呆、暂停；
- 具备防护：事件防抖（亮屏 2 秒 / Wi-Fi 6 秒）、连续失败冷却（3 次 / 600 秒）、SIM PIN 拒绝注入、跨进程互斥 + 1.5 秒去重、单实例目录锁；
- 可观测：每轮解锁记录 `lock / presence / inject` 三段耗时与触发来源。

### 19.3 相比国内厂商的「蓝牙智能解锁」

厂商方案的硬限制：

1. **生态锁定**：可能只认自家品牌手表/手环，第三方耳机、音箱、别家手环无法加入信任列表（当用私有配对与身份校验，第三方接不进去）。
2. **功能固定**：没有 Wi-Fi 联动，做不了「必须在家才解锁」这类约束。
3. **没有多设备组合**：通常只支持单个设备，做不到「多设备同时在线才解锁」。
4. **ROM 强绑定**：系统升级后行为可能变化，部分机型直接阉割开关。

本应用：

- **无品牌锁定**：任意已配对蓝牙设备都能勾选；
- **组合条件自由**，例如：
  - 场景 A：连上家里 Wi-Fi 就解锁，不需要蓝牙；
  - 场景 B：手环在线 **且** 连着家庭 Wi-Fi 才解锁（外出即使蓝牙连着也不解）；
  - 场景 C：多个蓝牙设备**全部在线**才解锁，安全性更高；
- **Wi-Fi 连接检测**是独立能力：读取当前已连接 SSID（`wifi_trusted` 校验），既可当触发源（连上可信 Wi-Fi 且屏幕已亮已锁时触发一次），也可当必要条件；列表只接受「当前已连接」的网络，避免手动填错；
- 跨厂商、跨 ROM：HyperOS、LineageOS、国行无 GMS 机型都能跑；
- 解锁后可自动打开指定 App，或右滑回到原界面（音乐锁屏更友好）；
- 三条授权通路覆盖不同人群：Shizuku（默认）、Root、内置无线调试（不 root、不装 Shizuku，也不需要电脑）。

### 19.4 架构层面的差异

1. **解锁逻辑放在 shell 脚本里，App 只是配置外壳**：应用被系统杀掉后守护仍然工作；应用不在时，在线缓存会自动退化为「亮屏现查蓝牙」，不会直接失效（`present_ok_fast()` 里会检查 `app_alive`）。
2. **缓存与实时查询结合**：应用监听蓝牙/Wi-Fi 广播维护在线缓存，亮屏优先读缓存；缓存不可信或应用不在时现场查询。实测解锁耗时 **550～1070ms**（小米 15 / HyperOS，版本 1.0），并内置 `--bench` 可复测。
3. **规避锁屏兼容性坑**：用 `wm dismiss-keyguard` 直接拉起 PIN 键盘，而不是模拟上滑，避免音乐锁屏、第三方锁屏吞掉手势。
4. **自检与调试链路完整**：`--check` 输出条件与状态，`--bench` 测各命令耗时，日志自动轮转；出问题能定位到「蓝牙条件 / 锁屏判断 / 注入」哪一环。系统原生方案几乎没有用户可访问的调试手段。

### 19.5 边界与客观短板

- 仅支持**纯数字 PIN**，图案/混合密码无法注入；
- PIN 以明文保存在配置文件（应用私有目录 + `/sdcard/watch-unlock/config.conf`），拿到 shell/root 的人可读；
- 可能在**重启后失效**，需要重新打开并配对；
- 读不到穿戴设备的佩戴传感器，只要蓝牙连着就可能解锁（与多数厂商普通模式一致）；
- 不是系统级 `TrustAgent`，安全边界低于厂商的 TEE 校验方案——它解决的是「可用性/自由度」，不是「更高安全性」。
