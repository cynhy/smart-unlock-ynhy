# 蓝牙设备解锁 3.3：三档授权，没有 Shizuku 也能用

> 适用：Android 8.0 及以上（minSdk 26），目标 Android 14。
> 效果：勾选的蓝牙设备或 WiFi 在场时，亮屏自动输入 PIN。
> 三种授权方式任选：Shizuku、Root、无线调试。最后一种既不需要 root 也不需要 Shizuku。

---

## 一、概述

### 1.1 它能做什么

装一个 APK，选授权方式，勾选设备，输一次 PIN。之后每次亮屏，只要条件成立就自动完成解锁。

| 能力 | 说明 |
| --- | --- |
| 三档授权 | Shizuku（默认）/ Root / 无线调试，设置页随时切换 |
| 亮屏解锁 | 监听亮屏事件，条件成立后唤键盘并注入 PIN |
| 蓝牙条件 | 任意已配对设备，可多选，任一在线或全部在线 |
| WiFi 条件 | 可作为独立解锁条件，也可作为蓝牙的必要条件 |
| 音乐锁屏返回 | 解锁后可打开指定应用，或向右滑动回到原界面 |
| SIM 卡 PIN 防呆 | SIM 处于 PIN 锁定时跳过，避免把手机 PIN 输进 SIM 界面 |
| 震动反馈 | 按键与开关有轻微震动，可关闭 |
| 公告栏 | 测试版说明、注意事项、开源组件鸣谢 |
| ADB 命令行 | 无线调试页顶部可直接执行 `adb shell` 命令 |
| 中英双语 | 跟随系统语言，可手动切换 |

### 1.2 三种授权方式怎么选

| 方式 | 需要什么 | 稳定性 | 适合 |
| --- | --- | --- | --- |
| Shizuku | 装 Shizuku 并授权，重启后需重新激活 | 最稳 | 大多数用户 |
| Root | Root 管理里授权本应用，无需 Magisk 模块 | 稳，但依赖 Root 实现 | 已 root 的设备 |
| 无线调试 | 系统「无线调试」里配对一次 | 依赖端口与配对状态 | 既不想装 Shizuku 也不能 root |

三种方式执行的都是同一套守护脚本，区别只在「谁给 shell 身份」。切换后守护会自动重启。

无线调试这一档内置了 Kadb ADB 客户端，所以不需要电脑，也不需要 Shizuku。代价是包体变大（见 3.1）和配对步骤。

### 1.3 前提

1. 锁屏方式是 **PIN 码**（纯数字）。图案、混合密码不支持。
2. 设备已在系统蓝牙设置里完成配对，或 WiFi 已连接过一次。
3. 所选授权方式可用（Shizuku 在运行 / 已授予 Root / 无线调试已配对）。

## 二、原理

### 2.1 为什么必须借 shell 身份

Android 的锁屏属于安全窗口，普通应用和辅助功能都无法注入事件。只有 `uid 2000(shell)` 的进程持有 `INJECT_EVENTS`，能向安全窗口注入按键。

三种授权方式本质是三条拿到 shell 的路径：

1. Shizuku 通过 ADB 或 root 启动一个 shell 服务，把通道借给应用。
2. Root 直接 `su -c`。
3. 无线调试用内置 ADB 客户端连本机，等价于自己给自己一条 adb 通道。

### 2.2 一次解锁的时序

```
屏幕点亮 → power_screen_state 事件
  ├─ 防抖 2 秒
  ├─ 读在线缓存 wu.present        40～110ms
  ├─ 判断是否锁屏                  10～50ms
  ├─ （可选）SIM 锁定检查           5～10ms
  ├─ wm dismiss-keyguard           约 50ms
  ├─ 等待 0.1 秒                   100ms
  ├─ input text <PIN>              150～220ms
  ├─ 复核焦点，成功即刻返回
  └─ （可选）音乐锁屏返回：打开指定应用 或 向右滑动
```

3.x 在末尾加了一步「返回」，其余部分与 1.x 相同。

### 2.3 两分钟可行性自测

1. 锁屏并上滑，调出 PIN 键盘。
2. 用当前授权方式执行 `input keyevent 8`（数字 1）。
3. 观察右下角按钮，正常会从「返回」变成「删除」。

变了说明注入有效；没变说明这条授权通道没打通。

## 三、安装

### 3.1 安装包与体积

| 文件 | 版本 | 体积 | 签名证书 |
| --- | --- | --- | --- |
| `watch-unlock-3.3-official.apk` | vc33 / 3.3 | 3.16 MB | `CN=ynhyttmy@qq.com` |
| `watch-unlock-3.0-test.apk` | vc30 / 3.0 | 3.16 MB | `CN=smart unlock beta` |

包名统一是 `com.watchunlock.app`，minSdk 26，targetSdk 34，签名方案 v2 + v3。

体积从 1.x 的 84.7 KB 涨到 3.16 MB，唯一原因是内置了 Kadb ADB 客户端及其依赖（9 个 jar）。不用无线调试这一档也得跟着变大，因为打包时去不掉。

### 3.2 两个包的区别

内容完全一致，只有清单里的版本号不同（编译时替换，源码不动）。

**签名不同，所以不能互相覆盖安装。** 从 3.0 测试版切到 3.3 正式版，必须先卸载，应用内配置与设备勾选会被清空。

```sh
adb uninstall com.watchunlock.app
adb install watch-unlock-3.3-official.apk
```

从 1.x 升级同理，签名不一致也要先卸载。

### 3.3 安装

```sh
adb install -r watch-unlock-3.3-official.apk
```

小米 / 红米可能报 `INSTALL_FAILED_USER_RESTRICTED`，是「USB 安装」开关没开：

1. 开发者选项 → 打开「USB 安装」；
2. 或 `adb push` 后 `pm install -r`。

### 3.4 首次启动的授权

按所选方式不同：

1. **Shizuku**：弹框选「始终允许」。`pm grant` 对它无效。
2. **Root**：在 Root 管理器里给本应用授权；开发者选项的 Root access 需设为「Apps and ADB」，否则 Root 档显示不可用。
3. **无线调试**：设置页选「无线调试」→ 点跳转按钮到系统页面 → 打开开关 → 配对。

另外还需要「附近的设备」权限（Android 12+），用于监听蓝牙广播。拒绝也能用，只是退化成每次亮屏现查。

## 四、界面与配置

### 4.1 主界面

四块：状态卡、蓝牙设备、解锁条件、操作区，右上角「设置」。

状态卡显示守护状态、当前授权引擎、条件摘要和一行实时状态。

### 4.2 蓝牙设备

每个已配对设备一行：名称、MAC、连接状态、启用开关。新设备默认不勾。

HyperOS 上 MAC 会被脱敏，界面同时接受完整 MAC、设备名、MAC 末五位三种匹配。

### 4.3 解锁条件

- 多设备模式：任一在线 / 全部在线。
- WiFi 独立解锁：连上指定 WiFi 即可解锁，不需要蓝牙。
- WiFi 作为蓝牙必要条件：蓝牙成立之外还必须连在指定 WiFi。
- WiFi 列表：**只能添加当前已连接的网络**，不支持手动输入 SSID。想加别的网络，先连上去再点「添加当前 WiFi」。

### 4.4 设置页

**授权引擎**：三档切换，切换后自动重启守护。

**解锁增强**
1. SIM 卡 PIN 防呆：默认关闭。开启后每次亮屏多 5～10ms 检查，SIM 处于 PIN 锁定时跳过本次解锁。
2. 震感反馈：按键与开关的轻微震动，可关闭。

**音乐锁屏返回**
解锁后可执行两种动作，可单独启用，也可同时启用：

1. 打开指定应用（填包名，例如 `com.tencent.mm`）；
2. 向右滑动，回到解锁前的界面。

两者同时开启时，优先打开应用；打开失败才走滑动。

**无线调试**
顶部是 ADB 命令行输入框，可直接执行 `adb shell` 命令并回显退出码与输出；下面是「跳转系统无线调试页面」按钮和配对说明。

**公告栏**
测试包说明、注意事项、开源组件鸣谢（Apache-2.0、Bouncy Castle），点「开源组件」可看协议摘要。

## 五、实现细节

### 5.1 在线状态用事件缓存

应用监听蓝牙与 WiFi 广播，状态一变就调守护刷新 `/data/local/tmp/wu.present`；亮屏时只读这个文件。省掉每次 300～800ms 的现查。

缓存带可信校验：应用进程在、且登记过监听，才直接采用，否则现查。宁可慢，也不拿过期数据去解锁。

### 5.2 开门用 dismiss-keyguard

固定 `wm dismiss-keyguard` 唤出密码键盘，不走手势。早期版本靠上滑，会被音乐类锁屏吞掉事件，键盘根本不出现。

失败后的慢路径才回退上滑，并先清空可能已输入的位。

### 5.3 确认与保护

注入后用 `dumpsys window | grep mCurrentFocus` 复核，每次约 80ms，最多 12 次，成功立即返回。

保护措施：

1. 屏幕事件防抖 2 秒，WiFi 事件 6 秒。
2. 连续失败 3 次冷却 10 分钟。
3. 未唤醒、未锁屏不注入。
4. 显示熄屏（防误触）时跳过。
5. SIM 锁定且开启防呆时跳过。
6. 单实例保护：锁文件加 `ps` 精确匹配，防止两个守护抢着注入。

### 5.4 音乐锁屏返回的实现位置

这一步放在「确认已解锁之后」，所以不影响解锁速度。打开应用用 `am start`，失败则执行一次向右滑动的手势；实际走了哪条分支会写进日志。

## 六、从脚本到应用，再到三档授权

### 6.1 起点是 shell 脚本

最早的需求只有一件事：手表在时自动解锁。一个 `.sh`、Shizuku 身份、监听亮屏、注入 PIN，不到一百行，第一天跑通。

问题不在功能，而在每次加需求，脚本方案的成本就涨一截：配置变手工活（曾把分隔符打成中文逗号导致完全不触发）、临时操作要记命令、出问题只能看日志、分享门槛高。

### 6.2 包一层界面

最后的决定不是二选一，而是分工：**守护逻辑留在 shell，应用只做配置、广播、拉起、运维四件事**。

不用 Gradle 和 AndroidX，直接 `aapt2 → javac → d8 → zipalign → apksigner`。界面全用代码写，省掉资源编译。守护脚本放 assets，装的时候推到 `/sdcard`，保持脚本是唯一真相源。

这套决定带来的好处很直接：1.x 的包体只有 84.7 KB，构建十秒完成。

### 6.3 3.x 为什么要加两条新通道

用户反馈里有两类人用不了：

1. 不想装 Shizuku（嫌它重启后要重新激活）；
2. 装了 Shizuku 但某些 ROM 上激活不稳定。

于是加了 Root 和无线调试。前者是几行 `su -c`；后者要在应用里塞一个 ADB 客户端，也就是 Kadb。

**代价立刻体现出来**：包体从 84.7 KB 跳到 3.16 MB。这是三条通道里唯一一条需要额外运行时依赖的，但它换来的是「既没 root 也没 Shizuku 的人也能用」。

另一个代价是 Java 版本：Kadb 的 jar 是 Java 21 字节码，build-tools 34 的 d8 读不了，必须升到 36.0.0；编译期还要用 stub jar 骗过 javac，真实 jar 只交给 d8。

### 6.4 热路径始终没动

三档授权只是换了「谁执行命令」，解锁流程一行没改：缓存、判锁屏、唤键盘、注入、复核。所以 1.x 的实测数据对 3.x 依然有参考价值。

新功能全部塞进设置页或解锁之后，主界面保持四块，热路径保持五个动作。

## 七、实测与未验证

### 7.1 1.x 的实测数据（3.x 热路径未变）

| 项 | xaga（LineageOS 24 / Android 17） | 小米 15（HyperOS 3 / Android 16） |
| --- | --- | --- |
| `total` | 960 / 970 / 1000 / 1010 / 1030 / 1070ms | 550 / 570 / 660 / 670 / 700 / 730ms |
| `lock` | 30～50ms | 10～40ms |
| `presence`（缓存命中） | 40～110ms | 40～50ms |
| `inject` | 180～220ms | 150～180ms |

脚本侧只占 250～300ms，其余是 SystemUI 收 PIN、校验、播动画的时间。

### 7.2 3.x 的验证状态

必须说清楚：3.0 / 3.3 两个包**已完成签名并通过校验，但还没有在任何真机上跑过**。

已完成的验证只有：版本号、签名证书、包内组件存在性（Kadb、震动、公告、音乐锁屏文案、无线调试文案）。

尚未验证的项目：

1. 无线调试的**配对码流程**没实测过，2.x 只用过 `adb tcpip 5555`。
2. 无线调试跳转在 LineageOS 上找不到系统子页面，会回落到开发者选项首页，需要手动再点一次「无线调试」。
3. 音乐锁屏返回、震感开关都没做真人验证。
4. Root 档在测试机上显示不可用，需要先把开发者选项的 Root access 改成「Apps and ADB」。
5. ADB 命令行页的输入框无法用 `adb input text` 注入，功能本身未人工确认。

## 八、常见问题

**装了 3.3 但显示 3.0，或者干脆装不上**

3.0 测试版和 3.3 正式版签名不同，不能覆盖安装。先 `adb uninstall com.watchunlock.app`，再装新的。卸载会清空设备勾选和 PIN。

**无线调试选了但一直连不上**

1. 确认系统「无线调试」开关是开的（重启手机后会自动关闭，需要重新打开）。
2. 确认已在同一页面完成配对；配对端口和连接端口不同，以系统页面显示的为准。
3. 端口变化后需要重新配对。

**Root 档显示不可用**

开发者选项里的 Root access 要改成「Apps and ADB」，并且在 Root 管理器里给本应用授权。

**WiFi 列表里加不了别的网络**

只能添加当前已连接的网络。先连上目标 WiFi，再点「添加当前 WiFi」。

**开了音乐锁屏返回，结果打开的还是原应用**

检查包名是否写错。包名正确但应用未安装时，会退回到向右滑动，日志里会写明实际走的分支。

**震动关不掉**

设置页「震感反馈」开关；部分 ROM 的省电模式也会影响震动强度。

**SIM 防呆开了之后成功率变低**

预期行为。它在 SIM 锁定时跳过整次解锁。SIM 解锁一次后就不再拦人。

**应用要一直开着吗**

不用。解锁在 shell 守护里，应用只负责传状态和刷新通知。应用被清掉时，守护会在亮屏那一刻现查蓝牙，功能正常，只是慢一点。

**怎么彻底停掉**

设置页或应用内「停止守护」；「一键清理残留」会连配置目录一起删，但保留勾选。

## 九、安全说明

1. 本方案的本质是在特定条件下替用户输入锁屏密码，客观上降低了设备安全性。
2. 密码以明文存在 `/sdcard/watch-unlock/config.conf` 与应用私有存储中，文件管理器可见。
3. 无线调试档会让应用自身具备 ADB 能力，注意不要把这个包发给不信任的人。
4. 摘下手表后必须确认锁屏恢复正常，这是部署后第一时间要验证的。
5. 不要把 APK 连同自己的配置文件一起分发。

## 十、边界与已知问题

1. **只支持 PIN 码锁屏**，图案与混合密码不支持。
2. **无法判断设备是否戴在身上**，摘下放桌上只要没断连照样解锁。
3. **签名分两套**：测试版与正式版不能互相覆盖，切换必须卸载。
4. **3.x 尚未真机验证**，见 7.2 的清单。
5. **WiFi 只能添加当前网络**，换网络要重新添加。
6. **无线调试重启后失效**，系统会自动关闭该开关，需要重新打开并配对。

## 十一、日志与排查

日志页：设置 →「查看运行日志」，深色等宽字体、2.5 秒自动刷新，可刷新、复制、清空；超过 1MB 自动轮转。

正常一次：

```
present(cache): bt 1/1
timing: lock=40ms presence=50ms inject=210ms
result: unlocked (total=990ms)
```

跳过会写原因，例如 `skip: sim_locked`、`skip: 解锁条件不满足`。音乐锁屏返回会额外记录实际分支（打开应用 / 向右滑动 / 失败）。

状态自检：

```sh
adb shell sh /sdcard/watch-unlock/wu-daemon.sh --check
```

输出启用数、在线数、锁屏状态、授权引擎、WiFi、SIM、冷却与暂停剩余。
